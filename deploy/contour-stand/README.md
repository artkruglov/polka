# Стенд «Контур»: окружение для чужих агентов

Стенд показывает, как в компании работает окружение для сторонних ИИ-агентов (Codex, Claude Code, GigaCode). ИБ пишет **профиль задачи**, сотрудник ставит задачу, а **диспетчер** превращает её в запуск агента в изолированной песочнице. Запуск идёт по правилам профиля: кто может поручать, куда агенту можно выйти в сеть, какая модель и бюджет, какие секреты и права. Результат ждёт приёмки на Полке, а весь путь задачи записывается в журнал под её номером.

Поверх этого стоит **рой** ([ниже](#рой-компания-из-агентов)): сотни процессов компании записаны пакетами в каталоге, а агенты, проверки, политика и действия во внешних системах — общие для всех.

Это лаборатория на Mac, а не установка у заказчика: одна ВМ вместо Kubernetes. Предыдущий стенд — [agent-stand](../agent-stand/README.md): одна песочница `srt` и токены задачи Полки. Здесь вокруг агента добавлены остальные слои: доступ, шлюз моделей, секреты, сеть, внутренняя система, журнал и затраты.

```
Mac: Полка 127.0.0.1:4390 ──ssh -R──► ВМ Ubuntu 24.04 «contour» (Lima, без папок Mac)
                                     ├─ Docker: Keycloak · OpenBao · LiteLLM(+Postgres) · Gitea   (порты только на 127.0.0.1)
                                     ├─ Squid 10.77.0.1:3128 — единственная дверь из сети задач
                                     ├─ dispatcher.mjs (root) — профиль → задача → песочница → закрытие
                                     └─ task-net 10.77.0.0/24, internal: песочницы gVisor (runsc), по одной на задачу
                                          └─ Codex → шлюз LiteLLM (ключ задачи) · Gitea (токен добавляет прокси) · Полка (токен задачи)
```

## Профиль: строка → что включает

```yaml
delegate_role: delegate-bugfix   # Keycloak: без роли задача отклоняется ещё до запуска
sandbox: { cpus: 2, memory: 2g, ttl_minutes: 20 }   # gVisor; по TTL процесс убивается
network: { allow: [polka, model, git] }             # Squid: блок правил на адрес песочницы
model: { models: [agent-model], budget_usd: 1.5 }   # LiteLLM: ключ задачи с бюджетом
secrets: { git: agent-bot }                          # Squid подставляет токен из OpenBao
access: { polka_bot: report-bot }                    # Полка: токен задачи этого бота
approval: human                                      # результат ждёт человека на Полке
```

## Запуск

Нужно:
- macOS с [Lima](https://lima-vm.io) и примерно 20 ГБ свободного места: ВМ занимает около 15 ГБ.
- Полка этого репозитория с полками отделов и сервисными доступами: `TEAM_SHELVES=on SERVICE_ACCOUNTS=on npm run dev`.
- Боты из `deploy/agent-stand/seed.mjs`.
- API-ключ провайдера модели. Его вводит владелец стенда, и в чат он не попадает.

```bash
node deploy/agent-stand/seed.mjs --account .local/local-account.json   # полки и боты на локальной Полке
deploy/contour-stand/stand.sh up          # ВМ и всё внутри (первый раз ~15 минут)
deploy/contour-stand/stand.sh tunnel &    # Полка внутри ВМ по тому же адресу
deploy/contour-stand/stand.sh polka-bot   # токен report-bot → OpenBao
deploy/contour-stand/stand.sh secret      # провайдер, модель и ключ → OpenBao → LiteLLM
deploy/contour-stand/checks.sh            # проверки границ; ключ модели не нужен
deploy/contour-stand/demo.sh              # весь показ с агентом
```

Отдельные команды диспетчера (`stand.sh run …`):

```bash
stand.sh run run profiles/bugfix.yaml "Исправь падающий тест" --as ivanov
stand.sh run start profiles/bugfix.yaml "…" --as ivanov   # вернёт task_id сразу
stand.sh run revoke <task_id>                              # остановить сейчас
stand.sh run status
```

## Путь одной задачи

1. **Поручение.** Диспетчер берёт пароль тестового пользователя из OpenBao и входит в Keycloak. Подпись токена проверяется по ключам realm. Если в токене нет роли из профиля, задача отклоняется и записывается событие `identity/refused`.
2. **Модель.** LiteLLM выдаёт ключ только для этой задачи: модели из профиля, бюджет, срок на 5 минут дольше TTL. Ключ провайдера остаётся в шлюзе.
3. **Полка.** Сервисный доступ из профиля получает токен задачи (`POST /api/v1/task-token`).
4. **Сеть.** Песочнице назначается адрес в `task-net`, Squid получает блок правил на этот адрес.
5. **Песочница.** gVisor-контейнер с папкой задачи `/work`. В окружении есть только прокси, ключ задачи для шлюза и токен задачи Полки.
6. **Закрытие** — по завершении, по TTL или по `revoke`. Диспетчер записывает в журнал расход ключа, удаляет ключ, убирает сетевые правила, сводит записи Squid (сколько запросов, сколько отказов и куда), сохраняет журнал контейнера и удаляет его. Результат ждёт приёмки на Полке.

## Рой: компания из агентов

Процесс компании — это файл-пакет в `processes/`, а не отдельное внедрение. В пакете записаны:
- цель и владелец;
- ступень доверия;
- триггер: запрос словами, почтовый ящик или расписание;
- навык из маркета;
- действия во внешних системах и с какой ступени они идут без человека.

Всё остальное общее: шина, песочницы, проверки, политика, шлюз действий, Полка.

```
цель словами · ящик процесса · расписание + папка
        └► swarm.mjs: приём → процесс из каталога → NATS work.<пул>
              └► песочница: навык (скрипт или агент) → /work/out: результат и предложенные действия
              └► песочница без сети: проверки навыка
              └► OPA: кто принимает результат, какие действия проходят (policy/)
              └► Полка: версия, которую принимает человек (событие revision.accepted)
              └► шлюз действий → systems.mjs: реестр операций, ЭДО, почта (ключ идемпотентности)
              └► подпись: только подписант и только принятая версия
```

| Что | На стенде |
|---|---|
| Пакеты процессов | `processes/*.yaml`: договор по КП, ответ клиенту из ящика `support`, выход сотрудника, план проекта; пятый — сверка оплат — создаётся при показе командой `new` |
| Маркет навыков | `catalog/skills/*`: `SKILL.md`, скрипт и проверки. В `catalog/index.json` записан digest, полученный при допуске (`catalog.mjs admit`). Если навык изменили после допуска, в песочницу он не попадёт |
| Шина | NATS JetStream 2.14.8: очередь `work.<пул>` на отдел, поток `events.>` |
| Политика | OPA 1.20.1: `policy/base.json` — границы ИБ, `policy/accept.rego` — ступени, лимиты, подпись, выборка на аудит. Действие с `human_only` в границах ИБ всегда решает человек, что бы ни написал пакет |
| Системы учёта | `systems.mjs` — только API, интерфейса для людей нет: счета, ЭДО с очередью подписи, почтовые ящики и исходящие. Писать в них может только шлюз; из песочницы — только GET через Squid |
| Расширения | другой стенд добавляет каталог навыков, пакеты и маршруты действий через `/etc/contour/extensions.json`. Маршрут с `"hook": true` — собственная запись стенда: её делает хук пакета (`effect`), а не система учёта, и только через шлюз |
| Люди | Keycloak: `petrova` и `orlova` — владельцы процессов, `director` — подписант, `ivanov` ставит цели и проекты, у `petrov` ролей нет |

**Ступени доверия.** 0 — черновик. 1 — каждый результат принимает человек. 2 — машина принимает типовое, человеку уходят расхождения и выборка 1 из 10. 3 — человек смотрит выборку 1 из 50. Действие с компенсацией (счёт можно отменить) идёт само со ступени, указанной в пакете, и в пределах лимита. Документ на подпись всегда принимает и подписывает человек. Когда человек принимает версию на Полке, этим же он одобряет действия, перечисленные в ней: второго «да» не нужно. `promote` повышает ступень только после 5 результатов подряд без отказа. Ошибка, найденная аудитом, опускает процесс на ступень вниз.

**Новый процесс.** Владелец описывает работу словами и прикладывает файлы прошлого периода вместе со своим ручным результатом (`expected.*`). Агент приёма ищет навык в маркете и собирает черновик пакета. Затем он прогоняет черновик в тени на этих файлах, сравнивает результат с ручным и кладёт черновик на Полку. Когда владелец его принимает, процесс встаёт в каталог на ступень 1. На показе первый прогон пропускает частичную оплату (совпало 4 из 5). Петрова называет правило, и второй прогон совпадает полностью: 5 из 5.

```bash
deploy/contour-stand/stand.sh polka-bot reader-bot      # рой читает приёмку на Полке
deploy/contour-stand/swarm-demo.sh --account .local/local-account.json [--auto-accept]
deploy/contour-stand/stand.sh contour inbox --as orlova  # и любые команды swarm.mjs
```

Команды `swarm.mjs` (`stand.sh contour …`):
- `goal` — цель словами;
- `new` — новый процесс;
- `project` — план проекта, работает только с моделью;
- `inbox`, `decide` — что ждёт человека и его решение;
- `sign` — подпись;
- `processes`, `process` — каталог и метрики процесса;
- `map` — карта процесса по журналу;
- `promote`, `audit` — ступень доверия и выборочная проверка;
- `undo` — компенсация действий;
- `drop` — файлы в папку процесса;
- `mail` — письмо в ящик;
- `tick` — запустить расписание;
- `selftest` — проверки роя.

Без ключа модели процессы идут на скриптах навыков: схема работает, но агент ничего не решает сам. Когда ключ есть (`stand.sh secret`), тот же навык выполняет агент в песочнице. План проекта пишет только агент.

## Проверки (`checks.sh`)

Песочница профиля `probe` получает то же, что агент, и пытается выйти за границы. Каждая строка отчёта — «ok», если попытка отказана или граница сработала:

- ядро gVisor вместо ядра ВМ;
- интернет напрямую и через прокси, включая TLS (`CONNECT` запрещён);
- OpenBao, Keycloak и Postgres через прокси, порты ВМ мимо прокси;
- административный API шлюза с ключом задачи;
- Полка: без токена, выпуск нового токена токеном задачи, веб-API;
- Gitea: прокси действует от имени `agent-bot`, подменённый заголовок заменяется, push в `main` отказан, push в ветку проходит;
- бюджет: на модели-заглушке с ценой ключ останавливается после нескольких вызовов; модель не из профиля отказана;
- в окружении песочницы нет ни одного секрета стенда. Это сверяется снаружи, по настоящим значениям, и сами значения нигде не печатаются;
- пользователь без роли не может поручить задачу;
- отзыв останавливает процесс, удаляет ключ и закрывает сеть, время каждого шага замеряется;
- рой (`swarm.mjs selftest`):
  - в системы учёта нельзя записать без токена шлюза;
  - шлюз не выполняет действие без решения политики, а повтор того же действия не создаёт второй счёт;
  - перевод денег, который мог бы предложить взломанный агент, политика отклоняет;
  - вердикт проверяющего на той же модели, что исполнитель, не засчитывается;
  - непринятую версию нельзя отправить на подпись;
  - токен агента не может принять версию на Полке;
  - навык, изменённый после допуска, не проходит.

Проверки Полки на чужую полку и права ботов — в [`agent-stand/bypass.sh`](../agent-stand/bypass.sh); здесь они не повторяются.

## Чего стенд не показывает
- **Рой без модели не думает.** Без ключа шаги выполняют скрипты навыков, а приём сопоставляет запрос с процессом по ключевым словам. Агент, который пишет навык или пакет по описанию, появится вместе с ключом модели. План проекта без ключа не работает совсем.
- **Человек на Полке один.** Приёмку делает аккаунт локальной Полки. Связи «владелец процесса в Keycloak = человек на Полке» нет: Keycloak проверяет только команды `decide`, `sign` и `promote`.
- **Проверяющий агент не запущен.** Политика умеет не засчитывать вердикт проверяющего на той же модели, но на стенде одна модель, поэтому пакеты проверяющего не требуют.

- **«От имени» проверяется только на входе.** Право поручать проверяет Keycloak, но токен Полки выдаёт сервисный доступ бота, а не обмен токена Иванова (RFC 8693). Связать их — следующий шаг Диспетчера.
- **Учётки — тестовые.** Пароли пользователей сгенерированы, лежат в OpenBao, и диспетчер входит за них (password grant). У заказчика человек входит сам, через SSO.
- **OpenBao с одним ключом распечатывания.** Ключ и root-токен лежат в `/etc/contour/bao-init.json` (только root), диспетчер читает секреты root-токеном. У заказчика — auto-unseal и AppRole.
- **Разрешённые адреса остаются каналом для данных.** Всё, что агент прочитал, он может отправить в модель, в Gitea или на Полку. Политику данных (например, OpenAPPA) стенд не проверяет.
- **Затраты — только модель.** Время песочницы, повторы и время человека на приёмку пока не считаются. Цена принятого результата появится, когда приёмка на Полке будет связана с задачей.
- **Токен задачи Полки нельзя отозвать отдельно.** При отзыве задачи процесс убит и сеть закрыта, но сам токен живёт до конца срока. Отключить можно весь сервисный доступ (`agent-stand/revoke.mjs`).
- **Диспетчер работает от root.** Доступ к Docker равен root. У заказчика это отдельный сервис с правами только на свой namespace.
- **Одна машина, Docker вместо Kubernetes**, образы скачиваются из интернета. Работа без интернета и SBOM — задачи поставки Контура.
