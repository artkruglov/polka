# Hosted viewer: ограниченный переход к staging

20.09.2026. Delta к [LIVE_VIEWER_SPEC](LIVE_VIEWER_SPEC.md) и [ARCHITECTURE](ARCHITECTURE.md). Это контракт эксперимента, не разрешение production и не изменение R06. HTML/CSS/JS остаются целью; оригиналы и производные различаются, неподдержанное содержимое сохраняется без ложного ready. Код этим документом не меняется.

## Текущее состояние реализации

21.09.2026: реализованы `HTML_LIVE_MODE=disabled|local|staging` и строгий staging allowlist immutable revisions. Runtime прошёл локальные проверки: [протокол](reviews/2026-09-21-viewer-staging/README.md). В режиме local `viewer-config.ts` сохраняет http://127.0.0.1 и http://localhost с противоположными hostname, совпадением listener/origin port и разными портами; staging допускает отдельные HTTPS origins, но оба upstream listeners всё ещё loopback. Это не просто dev-default: gate не даёт распространить локальную частичную проверку на публичные пользовательские документы. `main.ts` поднимает два Fastify listener; JS документа выполняется в браузере, не в viewer Node process. Отдельный listener защищает маршрутизацию, но не доказывает отдельный браузерный процесс, ограничение CPU или запрет всех исходящих соединений.

Уже есть: opaque iframe `sandbox="allow-scripts"`, отдельный viewer без session plugin/API/SPA, короткий DB-backed grant, повторная авторизация чтения pinned revision/derivative, CSP и запрет прямого top-level document через Fetch Metadata. Не проверены настоящий HTTPS proxy chain, cookies между двумя сайтами, полный navigation/egress корпус и browser responsiveness на hosted. Предыдущий внешний counter не годится как отрицательное доказательство: его positive control тоже был ERR_BLOCKED_BY_CLIENT.

## Минимальная реализация staging

| Участок | Конкретный delta |
|---|---|
| Config gate | Реализован явный режим `disabled/local/staging` с default disabled и сохранением нынешних local validations. Staging разрешать отдельным осознанным параметром, не автоматически при любом HTTPS. APP_ORIGIN и VIEWER_ORIGIN — нормализованные HTTPS origins без credentials/path/query/fragment, разные registrable domains. Проверять public suffix корректным PSL parser, не последними двумя labels. `COOKIE_SECURE=true` обязательно. Public origin ports больше не обязаны совпадать с внутренними listener ports. |
| Домены | Два принадлежащих оператору независимых registrable domains, например app на одном, viewer на другом; два поддомена одной зоны не удовлетворяют этому контракту. Viewer domain выделен только под этот runtime: без другого сайта, login, аналитики, customer content routes и service worker. Не использовать временный shared-hosting hostname без понятного контроля домена. |
| Proxy/upstream | App vhost → app listener, viewer vhost → viewer listener; неизвестный Host/SNI → отказ. Viewer upstream недоступен напрямую из интернета. В `live-viewer.ts` дополнительно сверять разрешённый Host; proxy передаёт фиксированный ожидаемый Host. Не доверять произвольным X-Forwarded-Host/Proto; forwarded headers задаёт только известный proxy. Не переписывать `Sec-Fetch-*`. Viewer не имеет SPA fallback, `/api`, `/mcp`, login redirect или public bucket redirect. |
| TLS/ответы | HTTPS viewer URL выдаётся сразу, без redirect цепочки на capability path. HTTP viewer document отклонять без Location с токеном. TLS и HSTS на обоих доменах; CSP/no-store/nosniff/no-referrer/frame-ancestors сохраняются на ответах через proxy. Viewer не получает X-Frame-Options DENY/SAMEORIGIN от общего шаблона proxy: это сломает разрешённое cross-site embedding. Не добавлять CDN/WAF HTML injection. |
| Cookies | App session остаётся host-only, HttpOnly, Secure, SameSite=Strict, Path=/, без Domain. Третий-party cookie для viewer не нужен. Proxy не пересылает Cookie/Authorization на viewer и удаляет случайный Set-Cookie из его ответа; viewer не принимает их как основание доступа. На app route выдачи grant действуют прежние session/Origin проверки. Не добавлять allow-same-origin или CORS ради исправления отображения. |
| Cache/logs | Отключить cache на всех viewer responses, включая ошибки; не кешировать grants/resolve. Viewer proxy/access/error/APM/WAF logs не сохраняют capability path, query, Referer или Cookie. Для наблюдения — нормализованный route, status и request ID, без token; CSP reports также могут содержать document URL и требуют редактирования. Нельзя включать full-URL logging ради negative tests. |
| Отключение | Staging flag проверяется при issuance и read; выключение запрещает новые чтения даже старых grants. Статика/download/export остаются прежними. UI/capabilities сообщают staging experimental и точный runtime profile; `htmlRuntime=true` и production readiness не выставлять на основании deployment. Локальный UI-текст не переносить буквально на hosted. |

Граница delivery остаётся простой: отдельный viewer upstream. Разделение backend процессов/прав можно выполнить при упаковке, но оно само по себе не ограничивает JS в браузере. Нельзя считать network policy контейнера защитой от browser egress. Для первого staging эксперимента использовать управляемые тестовые аккаунты и тестовые материалы; публичное включение для произвольных uploads ждёт runtime acceptance.

## Grants, CSP и навигация

Модель grants не менять: owner session или recipient source grant, максимум60 секунд, точные revisionId/derivativeId/source hash/builder/runtime profile, повторные expiry/logout/revoke checks при каждом чтении. Original share token, MCP token и app session не попадают в iframe. Capability URL — краткосрочный bearer на чтение одного документа, видимый самому документу; это не одноразовый token и не credential клиента. Уже загруженные bytes отзыв не уничтожает. Старый iframe остаётся на прежней версии после publish.

Сохранить текущий HTTP CSP viewer и sandbox attribute, parent `frame-src` с точным viewer origin, app `frame-ancestors 'none'`. Parent policy сейчас также разрешает `'self'` ради static previews: self-navigation из viewer на app origin может отправить запрос до отказа в embedding. Opaque sandbox и app frame-ancestors должны сохранять запрет чтения app DOM; это не доказательство отсутствия самого запроса. App endpoints не должны выполнять mutations по GET, а обычные mutations сохраняют Origin/session checks. Проверить app navigation с session cookie отдельно, не полагаться на предполагаемое поведение SameSite.

`frame-src` имеет проверки запроса и ответа; `frame-ancestors` проверяет допустимость embedding ответа. Поэтому ошибка отображения после redirect ещё не доказывает, что внешний запрос не состоялся. Сохранить browser gate `Sec-Fetch-Dest: iframe` + `Sec-Fetch-Mode: navigate`, отсутствие metadata → отказ. Эти заголовки предназначены для браузерного контекста, но клиент вне браузера может их подделать; authentication остаётся grant. Основания: [CSP frame-src](https://www.w3.org/TR/CSP3/#directive-frame-src), [CSP frame-ancestors](https://www.w3.org/TR/CSP3/#directive-frame-ancestors), [Fetch Metadata](https://www.w3.org/TR/fetch-metadata/#sec-fetch-dest-header), [HTML sandbox](https://html.spec.whatwg.org/multipage/browsers.html#sandboxing).

Не объявлять `connect-src 'none'` универсальным firewall. Проверять также RTCPeerConnection/STUN и resource hints. В актуальном draft CSP есть отдельная `webrtc 'block'`; наличие текста в стандарте не доказывает поддержку браузером, и неизвестная directive игнорируется. Не принимать её как достаточное исправление без проверки выбранных браузеров. [CSP WebRTC](https://www.w3.org/TR/CSP3/#directive-webrtc).

## Acceptance: что именно записать

1. **Deployment/config:** реальные домены/TLS; отклонение same-domain/non-HTTPS/insecure-cookie/неизвестного Host; viewer origin не обслуживает app/API/MCP и не ставит cookies. Проверить ответы у внешнего proxy, а не только app.inject. Cross-site iframe работает при блокировке third-party cookies.
2. **Сохранение и взаимодействия:** реальные сохранённые calculator/report/chart/slides/planner и multi-file team-report; upload/build → owner → unlisted recipient, ширина390 и1440, ожидаемые изменения данных, Stop/restart, оригинальный export побайтно прежний. Зафиксировать отдельные результаты single-inline и bundle derivative profiles.
3. **Авторизация:** чужой tenant, случайный/expired token, source grant expiry, owner logout/disable, share revoke, предыдущая версия после publish, выключенный runtime. Повтор после revoke не получает bytes ни через proxy cache, ни другой backend replica. Проверить отсутствие cookie/API secret в viewer запросах и документе.
4. **Изоляция браузера:** parent DOM, cookies/storage, fetch/XHR/beacon/WebSocket/EventSource, image/script/CSS resources, forms, popup/top navigation, nested frames/workers. Отдельно self-navigation через location/anchor/meta refresh, data/blob/about:blank, app origin и цепочки redirects на внешнюю цель. Добавить WebRTC/STUN и dns-prefetch/preconnect. Каждый probe использует только случайный тестовый marker, не настоящие данные.
5. **Достоверный egress контроль:** собственный третий origin со счётчиком/redirect endpoint и необходимые DNS/сетевые наблюдения. Сначала положительный контроль вне sandbox в том же браузере и сети действительно достигает collector; затем marker попытки из iframe и сопоставление server counters/browser events. Ноль без работающего positive control, DNS error или blocked render не считается успехом. Не выводить capability в collector; отдельный marker достаточен. Для redirect через viewer использовать только отдельную тестовую конфигурацию, не добавлять production open redirect.
6. **CPU/UI и матрица:** ограниченный hostile loop/DOM corpus, отзыв/Stop и responsiveness родителя, память/восстановление; terminating server build worker не останавливает уже исполняемый browser JS. Зафиксировать реальные версии Chromium, Firefox, Safari/WebKit и целевые мобильные платформы. Проверенный браузер не доказывает безопасность остальных. Если необходимое ограничение не действует, фиксировать незакрытую runtime acceptance, а не переключать silently в static-only и объявлять R06 выполненным.

## Решения, которые ещё нужны ведущему

- Выбрать конкретные два домена, TLS/proxy/staging host и доступ оператора; без этого HTTPS delivery/cookie acceptance не выполнена.
- Обеспечить рабочий независимый collector и browser matrix. До этого «без произвольного egress» не доказано; одних CSP violations недостаточно.
- По результатам CPU/egress эксперимента решить, достаточен ли этот browser execution profile для обещанного hosted runtime. Если нет — текущий gate остаётся закрытым для выпуска и требуется более сильная граница исполнения/сети; настоящий интерактивный HTML остаётся целью, production не объявляется готовым.
