## Границы сессий и целей — правило пользователя, 21.09.2026

Этот раздел имеет приоритет над историческими порядками исполнения ниже.

- Одна сессия обслуживает один ограниченный результат: локальное исследование → реализация → проверка. Новая реплика пользователя сама по себе не повод создавать новую сессию.
- При смене основного типа работы (проектирование → реализация, backend → UI, код → медиа) переходить в новую сессию с коротким handoff. После тяжёлого браузерного цикла, большого исследования или медиа-производства по умолчанию завершать срез и передавать следующий результат в свежий контекст.
- Цель этапа завершать только после проверяемого результата. Команда `/goal clear`, если пользователь применяет её в интерфейсе, не является доказательством завершения. Незавершённый общий объём не отмечать выполненным ради очистки контекста; сохранять остаток в плане.
- Одновременно один исполнитель: Luna medium — UI и небольшие изменения по готовому контракту; Sol medium — backend/MCP, права и миграции; Astra — границы задачи и точечное ревью. Минимальный контекст, без полной истории.
- Не повторять успешные проверки без нового изменения или найденного риска. Полный набор — на интеграционной границе. После сдачи пакета исполнитель останавливается; без автоматической цепочки новых аудитов.
- Не обещать численный лимит токенов, если он не задан и не установлен. Разделение сессий сокращает перенос контекста, но не гарантирует конкретную экономию.

### Этапы функции шаблонов

1. Модель шаблонов и доступа: контракт и критерии приёмки.
2. Сервер/MCP: реализация контракта и изолированные проверки.
3. UI: интерфейс по принятому серверному контракту.
4. Приёмка: один согласованный проход UI/API/MCP, исправление конкретных дефектов и фиксация ограничений.

Уже сделанное не повторять ради этой структуры. Текущая граница: сервер/MCP и UI реализованы; интеграционный набор прошёл 241 проверку, базовая браузерная приёмка зафиксирована в docs/reviews/2026-09-21-library-invitations/UI-ACCEPTANCE.md. Следующий один результат — реальный агент на демонстрационных данных находит библиотеку через MCP, получает точную версию шаблона и использует её для новой задачи. Этот результат теперь подтверждён: реальный Codex CLI + Luna через MCP получил четыре точных исходника и создал синтетический отчёт (reviews/2026-09-21-library-invitations/real-agent-result.json). Отрицательные UI-состояния viewer проверены (UI-ACCEPTANCE.md). Финальная сверка, файловый составной сценарий и сохранение отдельного результата через MCP завершены (TEMPLATE_ACCEPTANCE_AUDIT.md). Следующий один результат — безопасное локальное обновление schema21→26 с резервной копией и проверкой запуска; не повторять интеграционный набор без изменений. Рабочую базу schema21 не мигрировать в рамках этой проверки. Активная общая цель остаётся незавершённой, пока её критерии не выполнены.

Новый контекст не означает автоматический запуск ещё одной задачи или агента: сначала handoff и остановка завершившегося исполнителя. Не создавать цепочку дополнительных аудитов. В этой среде инструмент цели позволяет менять статус, но не переписывать активную цель или сбрасывать её бюджет; правила применяются через связанный регламент, без фиктивного завершения цели.

### Короткий handoff (до 15 строк)

- Один завершённый результат и его ограничения.
- Репозиторий, ветка, коммит; если коммита нет — изменённые файлы и наличие чужих правок.
- Проверки: команды, результат, путь к доказательствам; что не проверено.
- Остаток и блокеры, которые нельзя потерять.
- Следующий **один** результат, критерий готовности и модель исполнителя.
- Какие ресурсы нельзя менять; какие процессы ещё работают.

## Приоритетный регламент текущего цикла шаблонов — 21.09.2026

Это действующий порядок для ближайшего пакета библиотеки шаблонов; все разделы ниже сохранены как исторические записи и не переопределяют его.

- Одновременно работает один исполнитель. Luna (low/medium) берёт локальные UI, документацию и fixtures по готовому контракту; Sol (medium) — ACL/membership, интеграцию и миграции по утверждённому контракту; Astra — только постановку границ и краткое ревью diff риска.
- Передавать минимальный контекст: без full history, повторного общего аудита и повторного запуска уже пройденных тестов. Полный прогон выполнять один раз на интегрированном пакете.
- После одной неудачной самостоятельной попытки передать старшей модели конкретное воспроизведение; совет моделей не устраивать.
- Ближайшая контрольная точка: Sol завершает уже начатые приглашения в библиотеку и только относящиеся к ним проверки. Затем краткое ревью Astra; следующий UI-пакет передаётся Luna по готовому контракту. Рабочую БД до приёмки миграций не менять; весь enterprise сразу не брать.
- Точные проценты экономии и жёсткий token cap не обещать: число не задано, а инструмент цели не меняет бюджет действующей цели. По повторному запросу пользователя продолжаем существующую active-цель без обнуления истории и без дублирования исполнителей. Каждый пакет заканчивается кратким результатом; новый общий аудит не запускаем.

# Как выполняем дорожную карту

20.09.2026. Это регламент исполнения [ROADMAP](ROADMAP.md), а не второй backlog. Новая цель Codex создана и активна. Пользователь разрешил делегирование задач менее мощным моделям.

## Роли моделей

|---|---|---|---|
| GPT-6 Astra | Начало этапа, изменение архитектуры/контракта, ревью готового пакета, неоднозначный дефект | R-ID, нужные файлы и конкретный diff, ограничения, тесты | Контракт, разбиение, список дефектов и решение о приёмке |

| GPT-5.6 Sol, medium/high | Связанные backend/UI изменения, миграции, интеграция; либо если Luna за две попытки не исправила конкретный дефект | Минимальный воспроизводимый пример и решения Astra | Работающая интеграция и регрессионная проверка |

Astra участвует постоянно на контрольных точках, но не дублирует каждую строку Luna. Иначе экономии не будет. Реальные затраты зависят от токенов, повторов и доступного тарифа; проценты экономии не обещаем. Названия моделей подтверждены доступным списком инструментов этой сессии, а не предполагаемой доступностью в любом аккаунте.

Общие возможности Astra сверены с [официальным руководством](https://developers.openai.com/api/docs/guides/latest-model). Распределение задач выше — наш рабочий выбор, не официальный benchmark моделей.

## Один цикл выполнения

1. Ведущий агент берёт следующую незаблокированную задачу ROADMAP. Astra определяет контракт и риск для авторизации, данных и выполнения HTML.
2. Задача делится на небольшие пакеты с непересекающимися файлами. Обычно один исполнитель Luna; второй — только при действительно независимой работе. Не запускать совет моделей ради каждой кнопки.
3. Исполнитель получает цель, R-ID, входные файлы, разрешённые изменения, критерии, проверки и список запретов. Весь чат заново не передаётся.
4. Исполнитель меняет код и запускает относящиеся к задаче проверки. Текст «готово» без результата не считается сдачей.
5. Ведущий смотрит diff и интегрирует; Astra проверяет границы безопасности, сохранность данных и соответствие пользовательскому пути. Автор изменений не единственный проверяющий.
6. Небольшие замечания возвращаются тому же исполнителю. После двух неуспешных попыток не повторять тот же промпт: Sol получает воспроизведение; Astra пересматривает контракт при системной проблеме.
7. Интеграционные проверки запускаются один раз на согласованном пакете. После прохода — STATUS и ссылка на evidence. Новый прогон нужен после изменения кода, ошибки или нового риска.

Не давать исполнителям одновременно менять package.json, общие контракты или миграции. Их интегрирует ведущий. Не сбрасывать чужие незакоммиченные изменения. Не менять модель корневой задачи или глобальные настройки молча: имя модели задаётся явно при запуске подагента.
