# План Opus: Полка для production и роста

Дата: 2026-09-14

## Решение продукта

Главная работа пользователя — сохранить полезную страницу, которую он сделал в Claude, ChatGPT или другом агенте, и отправить её человеку, у которого исходная ссылка не открывается. Полка создаёт независимую копию, показывает её в обычном браузере и выдаёт ссылку на конкретную версию. Получателю не нужны аккаунт в исходном сервисе или VPN до него; доступность самого домена Полки зависит от размещения и сети.

Публичная витрина, лайки и профили поддерживают discovery и возвращаемость, но не должны мешать сохранению по ссылке. Основной P0 — не социальная сеть и не полноценный редактор.

## UX и социальный слой

### P0: путь ссылки

1. Автор загружает HTML/ZIP или использует MCP capture. Импорт публичной ссылки Claude/ChatGPT остаётся best-effort до проверки конкретных источников: такие ссылки могут отдавать JS-оболочку, требовать вход или менять формат.
2. До сохранения видит название, размер, тип и короткий предпросмотр; личная копия закрыта по умолчанию.
3. После сохранения получает карточку с `Скопировать ссылку` и понятной пометкой версии.
4. По ссылке получатель сразу видит страницу. Над ней показаны отправитель (если автор разрешил), версия и дата; рядом доступны `Сохранить себе`, `Положить свою работу` и `Пожаловаться`. Для просмотра вход не нужен.
5. Автор может выпустить ссылку на текущую версию, отозвать её и сохранить следующую версию без подмены уже отправленного адреса.

В интерфейсе нужно держать две разные кнопки: `Сохранить копию` и `Открыть доступ по ссылке`. Это снижает риск случайно опубликовать личные данные.

### P1: витрина и лайки

Витрина — отдельная зона с только опубликованными снимками. Публичный просмотр и счётчик реакций доступны без входа. Лайк/реакция, сохранение к себе и жалоба требуют входа: это даёт один голос на человека, позволяет удалить свой голос и не превращает анонимные просмотры в накрутку. Вход можно сделать простым magic-link/OIDC в hosted-версии; в self-hosted это заменяется корпоративным OIDC.

Минимальные элементы карточки:

- живой предпросмотр или статичный fallback с заметной меткой;
- название, тип и тема;
- имя автора или «Редакционный пример»;
- `Открыть`, `Полезно` с числом реакций, `Сохранить к себе`, `Поделиться`, `Пожаловаться`;
- дата публикации и номер снимка.

Сортировки: `Популярные`, `Новые`, `Рекомендованные`. Для P1 достаточно серверного запроса с `score` и индексом. Популярность не должна быть простым абсолютным числом: используем time-decay, например `score = likes / pow(age_hours + 2, 1.2)`, и ограничиваем вклад одного аккаунта одной реакцией. Пока опубликовано меньше 200 работ, вкладка `Популярные` показывает новые и редакционные примеры, чтобы лента не застывала. Рекомендованные сначала строятся по теме и типу, без сложного ML.

Публикация проходит состояние `черновик → на проверке → опубликовано → скрыто`. Автор сам отправляет снимок; новые личные версии туда не попадают. Жалоба скрывает материал из рекомендаций до решения модератора, но не удаляет авторскую копию.

### Будущие социальные функции

Профиль автора показывает только опубликованные снимки, если автор включил публичное имя. Комментарии, подписки и совместное редактирование не входят в первый релиз: они создают модерационную и privacy-нагрузку, не усиливая основную работу со ссылкой.

## Модель данных для P1

Добавить миграции, не меняя смысл существующих immutable revisions:

- `publications(id, artifact_id, revision_id, author_id, title, description, task, kind, status, published_at, hidden_at, score, reactions_count)`;
- `reactions(publication_id, account_id, kind, created_at, UNIQUE(publication_id, account_id, kind))`;
- `reports(id, publication_id, reporter_id, reason, status, created_at)`;
- `moderation_actions(id, publication_id, moderator_id, action, reason, created_at)`;
- опционально `profiles(account_id, display_name, avatar_key, is_public)`.

Сохранение к себе создаёт новую авторскую копию с provenance `based_on_publication_id`; оригинальный снимок не изменяется. Публичный resolver принимает только опубликованный `revision_id`. Для unlisted share остаётся текущий токенизированный grant с отзывом и сроком действия.

## Telegram и агентный вход

Telegram — ускорение P1 после стабильного P0:

- `/start` создаёт или связывает аккаунт с короткоживущим кодом из Полки;
- пересланная публичная ссылка скачивается только по разрешённым HTTP(S)-правилам, показывается превью и ожидает подтверждения;
- HTML/ZIP принимается как файл с теми же лимитами размера и MIME, что и веб;
- бот возвращает receipt и ссылку на закрытую копию; публикация и включение публичной ссылки требуют отдельного подтверждения;
- `/revoke <id>` отзывает ссылку, `/stop` удаляет связь Telegram с аккаунтом;
- webhook с секретным токеном, allow-list доменов, rate limit, антивирус/архивная проверка и журнал событий.

MCP-команда `save_to_polka` должна вызывать тот же application service, что и веб и бот. Она не получает права публикации по умолчанию: агент может сохранить черновик, а включить доступ может только человек.

## Production в Яндекс Облаке

### Hosted Light

Целевой минимальный контур:

- домен в Yandex Cloud DNS, TLS через Certificate Manager;
- два stateless экземпляра web/API за Application Load Balancer (или эквивалентный managed ingress), чтобы отказ одного экземпляра не останавливал ссылки;
- Managed PostgreSQL с автоматическими backup и PITR согласно выбранному тарифу;
- Object Storage с versioning и lifecycle для immutable blobs, thumbnails и quarantine;
- отдельный worker для reconciliation, preview generation, moderation queue и Telegram webhook jobs;
- Lockbox для `DATABASE_URL`, S3 credentials, link-signing key и Telegram secret;
- Monitoring/Logging: latency p95, 4xx/5xx, upload failures, resolver denials, queue lag, storage bytes, DB connections, backup age;
- ежедневный restore-drill в изолированное окружение до production launch.

CDN включается только после измерения публичного трафика. Для приватных ссылок кэширование должно быть version-pinned и не должно обходить grant/revocation. Скачивание blob идёт через приложение или короткоживущий подписанный ответ после проверки прав.

Точные названия managed-сервисов и тарифы нужно сверить в аккаунте Яндекс Облака на этапе внедрения; архитектурные порты должны оставаться S3/Postgres/HTTP-совместимыми.

### Enterprise self-hosted

Компания разворачивает тот же контейнерный release в своём контуре. Public showcase по умолчанию выключен; наружные ссылки могут быть запрещены политикой. Поддерживаемые порты:

- Postgres 15+;
- S3-compatible Object Storage (Yandex, MinIO, Ceph, AWS S3);
- OIDC/SAML через identity adapter;
- SMTP или корпоративный IdP для входа;
- Docker Compose для 20–40 сотрудников; Helm/Kubernetes и HA-профиль — отдельный P2-пакет для нескольких департаментов.

Tenant isolation обязательна на уровне каждой выборки и object key. Для корпоративного режима нужны группы/роли, offboarding, audit export и политика retention. Конфигурация должна задаваться env/config schema без изменения исходников.

## Расчёт ёмкости: гипотеза, которую нужно проверить телеметрией

Базовый сценарий на 50 000 зарегистрированных пользователей:

| Допущение | 12 месяцев | 24 месяца |
|---|---:|---:|
| MAU / DAU | 10 000 / 3 000 | 15 000 / 4 500 |
| Новых авторов в месяц | 1 500 | 2 250 |
| Новых работ на автора в месяц | 4 | 4 |
| Новых логических работ | 72 000 | 180 000 |
| Среднее число версий работы | 2 | 2 |
| Средний blob одной версии | 1.5 MB | 1.5 MB |
| Blob storage с thumbnails и запасом | около 0.35 TB | около 0.9 TB |
| Metadata + audit + indexes | 2–8 GB | 5–20 GB |
| Публичные просмотры в день | 20 000 | 50 000 |
| Egress при 3 MB на просмотр | около 1.8 TB/мес | около 4.5 TB/мес |

Это не обещание нагрузки: если средний ZIP будет 5 MB или публикации станут вирусными, storage и egress вырастут пропорционально. При 20 000 просмотров в день средняя нагрузка мала, но пиковые 20–50 RPS на resolver и 2–5 RPS на запись требуют двух API экземпляров и очереди для тяжёлых preview/import jobs. Connection pool Postgres ограничиваем, начинаем с 2–4 vCPU и 8–16 GB RAM на API tier, а точные размеры выбираем после нагрузочного теста. Object Storage и CDN должны принимать основной egress; база хранит только metadata и audit.

До выбора тарифа нужно измерить просмотры на MAU, фактический размер ответа и цену egress. Таблица выше задаёт рабочую гипотезу; CDN и кэширование публичных снимков включаются до роста витрины, иначе API-инстансы будут обслуживать весь трафик.

Целевые SLO для Light: 99.9% доступности resolver за месяц, p95 API до 400 ms без загрузки blob, сохранение receipt не более 60 s для типовой HTML-страницы. P1 добавляет RPO ≤ 15 минут и RTO ≤ 1 часа после аварии; значения подтверждаются restore-drill.

## Переиспользование или greenfield

Начинать новый backend сейчас не нужно. В текущем репозитории уже есть проверенная доменная основа:

- Fastify app и origin/CSRF/security headers;
- Postgres schema с tenant, folder, artifact, immutable revision, upload receipt и audit outbox;
- S3-compatible storage с checksum, conditional write и version-pinned read;
- React/Vite entry flows, landing, import, recipient и showcase.

Стабилизировать и вынести за порты:

- `ArtifactRepository`, `ShareRepository`, `PublicationRepository`;
- `BlobStore` (S3/MinIO/Yandex adapter);
- `IdentityProvider` (local dev/OIDC);
- `Queue` (in-process для Compose, provider adapter для production);
- `PreviewRuntime` с allow-list и изоляцией HTML.

Текущий код следует разделить на application services и HTTP handlers, добавить structured errors и миграции. Greenfield имеет смысл только после пилота, если измерения покажут, что модель HTML-runtime или multi-tenant isolation требует другого ядра. Переписывание сейчас отложит ценность ссылки и потеряет уже проверенные инварианты.

## Open-source поставка

Репозиторий должен содержать:

- Apache-2.0 license и CONTRIBUTING/SECURITY;
- `deploy/compose.local.yml` для одной команды;
- Helm chart с values для Postgres/S3/OIDC, ingress и secrets;
- `.env.example` с безопасными дефолтами без credentials;
- миграции с lock и совместимостью N-1;
- health/readiness endpoints и smoke-test script;
- отдельный профиль `SHOWCASE_ENABLED=false`, `ALLOW_PUBLIC_LINKS` и retention policies;
- документацию backup/restore, upgrade и offboarding.

Первая self-hosted команда должна запускаться одной командой `docker compose up` с демо-данными и иметь проверенный upgrade N→N+1. Для режима «данные не выходят из контура» нужен явный `OUTBOUND_NETWORK=deny`/allow-list и smoke-test, который подтверждает отсутствие внешних запросов, а не только выключенная витрина.

Внутренний агент компании подключается через MCP gateway в её сети. Hosted Light не должен требовать передачи корпоративных данных внешнему агенту.

## Roadmap и критерии выхода

### P0 — стабильная ссылка (релиз Light)

- Реализовать надёжный HTML/ZIP upload и MCP capture; импорт публичной ссылки — best-effort для явно поддержанных источников с понятным сообщением, если источник не отдаёт содержимое.
- Сохранение, preview, receipt, pinned revision, link grant, revoke, noindex и rate limits.
- Добавить базовый HTML-safety scan (внешние формы, фишинговые паттерны, опасные URL), жалобу по токену ссылки без входа и возможность быстро скрыть ссылку.
- Сделать экран получателя самостоятельным: кто отправил (опционально), версия/дата, `Сохранить себе`, `Положить свою работу`, `Пожаловаться`.
- Deploy в Yandex Cloud dev/stage, домен/TLS, backup/restore drill.
- 10–20 пользователей проходят сценарий «сделал в чате → отправил → получатель открыл ссылку».
- Активация: ≥50% выпущенных ссылок открыты получателем в течение 48 часов; ≥30% авторов сохраняют вторую работу в течение 14 дней; receipt и копирование ссылки остаются диагностическими метриками; resolver success ≥99%.

### P1a — доставка и команда

- Telegram bot с подтверждением импорта и revoke.
- Простая командная Полка для 20–40 человек: приглашение, общая папка, роли viewer/editor, без обязательного SSO.
- Метрики: доля ссылок, открытых получателем, повторное сохранение и week-4 return.

### P1b — discovery

- `publications`, reactions, reports, moderation queue и сортировки.
- Витрина с популярными/новыми/рекомендованными, профиль и сохранение к себе.
- Для гостя действия `Полезно`, `Сохранить` и `Пожаловаться` заранее помечены как требующие входа (или жалоба по токену доступна без входа); автор получает уведомление о жалобе, SLA модерации задаётся явно.
- Метрики: доля опубликованных работ с хотя бы одним просмотром, reaction rate, report rate, время до первой реакции, week-4 return.

### P2 — корпоративный контур

- OIDC/SSO, группы и роли, audit export, retention, tenant admin.
- Helm/Kubernetes, HA Postgres/Object Storage adapters, migration/rollback runbook.
- MCP gateway с project-scoped permissions и внутренними агентами.
- Пилот одной команды 20–40 человек, затем несколько департаментов.

## Acceptance checklist

Уже показано в текущем прототипе: value-first landing, вставка ссылки/HTML/ZIP, preview, личная копия, unlisted/public wording, recipient view, витрина с темами и UI-отметкой «Полезно», Telegram/MCP entry screen.

Пока не готово и не должно маскироваться как готовое: production hosted server, реальный fetch/import по внешней ссылке, серверные реакции и сортировка по лайкам, Telegram webhook, MCP tool, OIDC/SSO, Yandex deployment, moderation queue и гарантия доступности домена из любой сети.

**Verdict:** развивать текущий код поэтапно, сохранив его upload/revision/share инварианты и вынеся provider adapters. Сначала выпустить измеримый P0 со стабильной ссылкой; только после подтверждения активации добавлять витрину, лайки, Telegram и enterprise-контур.
