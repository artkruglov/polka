## Архитектура: что упростить

1. **Три конвейера загрузки** (одиночный файл, пакет, проект) повторяют один и тот же сценарий: ключ идемпотентности, блокировка полки, приём, финализация, проверка, учёт. `artifacts.ts` (1782 строки) держит четыре ответственности. Единый модуль загрузок со стратегией по виду уберёт параллельный набор `*Bundle*`.
2. **Цикл storage → moderation → shares → artifacts** обходится десятком `await import()` (`storage.ts:58…107`, `content-moderation.ts:1172` и др.). Небольшой `moderation-state.ts` (isolated/purged) и события после коммита уберут его.
3. **`/api/resolve` живёт в `app.ts`** (1538 строк, 25 SQL). Вынести в сервис и общий `openLinkQuery` для четырёх просмотрщиков (app, static, project, live): сейчас восемь копий одного соединения shares/tenants/accounts.
4. **`moderation.ts`, `shares.ts`, `content-moderation.ts`** смешивают логику и печать для CLI оператора; механическое разделение без риска.
5. **Блокировка полки** (`lockShelf`, `FOR UPDATE` на tenant) берётся на каждую запись и сериализует всё в пределах полки. Это главный предел масштабирования на одну полку, но при 80 работах он невидим. Сначала измерить время ожидания, потом ослабить до `FOR NO KEY UPDATE` и выносить S3 и CPU из транзакции.
6. **Функция стирания аккаунта** переобъявлена в миграциях 017, 020, 023, 028, 030, 047. Нужен тест «таблица с `account_id`/`tenant_id`, не покрытая стиранием, — ошибка», иначе риск для приватности растёт с каждой таблицей.
7. Тесты: 28 файлов зависят от таймеров, нет линтера и покрытия, нет теста двух экземпляров приложения.

## Многоэкземплярность

Близко к горизонтальному масштабированию: лимиты, сессии, гранты просмотра, задания импорта уже в Postgres. Мешают:
- часовой обход `sweepBlocks` и `retryUnchecked` в каждом экземпляре (`main.ts:78-86`); `retryUnchecked` без блокировки удвоит платные вызовы модели;
- очереди в памяти процесса: проверка моделью, снимки обложек (`covers.ts`), потеря очереди при рестарте;
- письма модерации и комментариев отправляются после коммита без outbox: падение между коммитом и отправкой теряет письмо.

## Производительность и железо

По убыванию отдачи:

1. **Просмотрщик проектов.** Каждый подресурс: SQL авторизации на шесть таблиц, ещё 2–3 запроса и один GET из S3; на странице с 30 файлами это 90–120 запросов. Ответы идут с `no-store` (Caddy и Fastify), без `ETag`, без gzip на домене просмотра. Файлы неизменяемы по версии. Правки: кэш решения по токену на 5–15 секунд, `ETag` из хеша манифеста и `Cache-Control`, `encode zstd gzip` на viewer-хосте. Ожидаемо в 5–10 раз меньше запросов.
2. **Maintenance каждые 60 секунд запускает новый `node --import tsx`** (`maintenance-scheduler.ts:19`, `maintenance-child.ts`): около 1440 холодных стартов в сутки. Это то самое 15 % CPU на пустом сервисе. Один долгоживущий процесс уберёт расход.
3. **Каждая HTML-страница больше 16 КБ порождает свежий worker**, который заново загружает tsx (`html.ts:639`, `html-classify-worker.mjs`). Пул прогретых воркеров и сборка сервера в JS (запуск `node` вместо `node --import tsx`) уберут крупнейший расход CPU на сохранении и ускорят холодный старт. Не проверено: не нужен ли tsx где-то ещё, например для миграций.
4. **Память VM пересуммирована:** app 1,5 ГиБ + maintenance 0,75 + renderer 1,5 (если включить) + Postgres без лимита + tmpfs бэкапа 512 МиБ. Нужны лимиты Postgres, `NODE_OPTIONS=--max-old-space-size`, tmpfs бэкапа поменьше, renderer на отдельной VM.
5. **Видео идёт через приложение** (уже записано в `PROJECT_VIDEO.md`). Каждый Range заново проходит авторизацию (п. 1) и S3. Когда видео начнут смотреть часто, нужны короткие подписанные ссылки или CDN с равносильным сроком жизни для отзыва и блокировок.
6. **Финализация читает каждый файл из S3 последовательно** (`artifacts.ts:1533`), затем те же файлы читает модерация и обложки. Ограниченная параллельность (4–8), Range-GET для префиксов (обложки читают 64 КБ из 5 МБ), один проход с сохранением извлечённого текста.
7. **Обложки:** после смены `COVER_VERSION` все карточки пересчитываются лениво (шторм GET и воркеров); JPEG лежат в `bytea` и растят дамп. Складывать в S3, ограничить параллелизм.
8. **Экспорт версии** держит до 180 МБ в памяти (48 МиБ + base64 + JSON): два одновременных экспорта и рядом два воркера — риск OOM при лимите 1,5 ГиБ.
9. **Сборка esbuild:** один запуск за раз, таймаут 5 с, при занятости 429. Очередь с обратным давлением вместо отказов.
10. **Лимитер IP пишет в БД на каждый запрос** (`auth.ts:48`); `/api/resolve` открывает транзакцию с ~10 запросами и блокировками. Для IP-лимита достаточно токен-бакета в памяти, БД оставить для входа.
11. **Нет метрик рантайма:** ни очереди пула, ни задержки цикла событий, ни RSS, ни счётчиков S3. `ops-status` каждый раз перечисляет все объекты бэкапов. Это первый пункт: без него остальное не измерить.
12. Мелочи: у бакета объектов нет правила истечения неактуальных версий; SPA (2,2 МБ, чанки, `immutable`) в порядке.

**Не проверено:** утечка в очистке `content-model-budget:%` (`LIKE` по ключам, которые `limitAttempts` хеширует), реальное время ожидания блокировок, покрытие индексов `revisions` и `shares`.

## Продукт

Сильное: подключение агента одной фразой (MCP, плагин, `llms.txt`, `openapi.json`), неизменяемые версии и ссылка на версию, изоляция viewer, проверенное восстановление и внешний uptime, честная документация.

Слабое:
- **Автор не знает, открыли ли его ссылку.** `share_opened` считается, но виден только оператору.
- **Отдельную работу нельзя удалить навсегда**, корзина не освобождает квоту (`data-retention.md`, п. 3). Расходится с Политикой.
- **Обратной связи от получателя нет**: на проде `COMMENTS_MODE=owner-notes`, это решение из-за статуса ОРИ.
- **Ссылка на проверке без объяснений** для получателя и автора; автоблокировка выключена, решает один человек.
- **Видео включается SQL-ом оператора**, масштабируемого пути нет.
- **Коннектор:** не проверены ChatGPT, вход из Claude Code, отзыв подключения. Кэш инструментов claude.ai требует пересоздать подключение, пользователь этого не знает.
- **Сохранить артефакт по ссылке нельзя**, расширение Chrome не опубликовано.
- **Нет данных о работе петли получателя** («Попробовать бесплатно», «Сделать такую же»): собирается, но отчёта нет; интервью с пользователями не было.
- Весь сайт под noindex, нет SEO и embed; в ленте один куратор.

Риски: единственный оператор без замены (`incident-response.md`), уведомление РКН не подано, регистрация с любого домена без заключения юриста, одна VM с динамическим IP, всё в одном облаке, платная модель модерации на одном провайдере.
