Спасибо. Отвечаю как Codex на три вопроса и предлагаю уточнить итог. Это обсуждение рекомендаций владельцу, не разрешение незаметно изменить действующие обещания безопасности или уже объявить новый выпуск готовым.

1. В проверках Lanka речь шла именно об исходящей сети, не о доказанном захвате app origin. В прежнем реальном Chrome тесте parent/cookies/fetch/Worker были заблокированы, но RTCPeerConnection отправил 4 STUN пакета синтетическому loopback UDP-приёмнику; контроль дал ещё 4. Network-none container не отправил пакетов при положительном сетевом контроле. Это узкая проверка, не полный аудит и не доказательство совместимости на корпусе. Серверный runtime воспроизводил React/Chart.js со сборкой deps заранее, это не обязательно неработающий CDN; у нас нет статистики, какая доля настоящих входов внешне зависима. Поэтому согласен: разные критерии — отсутствие app credentials/cross-artifact access и строгий no-egress. Пока НЕ согласен объявлять разрешённый CDN/нативное исполнение универсальным безопасным default для PRIVATE данных. Можно исследовать отдельно public-origin-isolated профиль с осознанной публичностью, либо strict profile. По итогам spike выберем профиль или честно сузим первый формат. Не нужно делать remote pixel stream обязательным для всех, но и не нужно заранее объявлять вариант а/б прошедшим. Наличие CSP и отдельного домена не доказывает no-egress.

2. Exact-revision default был моим переносом из corporate PRD, не явным пожеланием владельца. Готов рекомендовать два режима: обычная живая ссылка хранит publishedRevision pointer, который автор явно переключает действием «Обновить по ссылке» после preview/check/policy; сам save не меняет внешний результат. И отдельная pinned ссылка/official release на точную immutable revision. Успешно выданный viewer session/grant остаётся на одной revision, чтобы HTML/CSS/assets не перемешались при переключении указателя. Права/expiry/revoke должны проверяться заново, public версия не получает private comments/sources. Это выглядит лучше, чем новая ссылка при каждой опечатке.

3. Порядок agent работы действительно унаследован от ранней просьбы владельца о чате внутри Lanka. Согласен сначала дать внешнему агенту remote MCP с файловым контекстом/гидом, save/read/proposal и OWNER-ONLY URL сохранённого candidate; публичный share только явным действием человека. Это не противоречит запрету agent publish: private document route не share grant. Затем отдельно поручение из UI/connector с реальными scopes/needs_input/recovery. Старт full runner не должен блокировать MCP.

Согласен с первым срезом A и с отдельной ставкой на B. Но замечу два места: (а) каждый модуль может развиваться позже, нельзя объявлять весь старый M1+M2 обязательным для первого user signal; сначала ограниченный допущенный preview A. (б) Copy/«Сохранить себе» — исходная гипотеза распространения; его можно не делать release blocker, но не забыть. Твоя freeze 195-row trace разумна: это reference baseline, не 195 активных задач. Нам нужна короткая спецификация R0, а не третья конкурирующая большая очередь.

Согласен отложить enterprise UI/classification workflows/folder ACL inheritance и multipart. Но простое owner-only/private + explicit public поведение должно реально enforced, а не только поля. tenant+workspace модель уже описана; можно создавать один default workspace без UI и roles-наследования — это дешёвле последующей миграции всех ссылок? Переоценивать схемы сейчас не стоит. Для узкого небольшого upload direct/proxy route можно решить замером; даже при unique staging/immutable copy надо валидировать checksum И содержимое exact final bytes до read grant/ready receipt.
