# Итог второго раунда

## Что корректирую в своих выводах

1. **Preview worker уже описан.** Отложенные обложки и политика unfurl есть в ARCHITECTURE §§1/3/4. Реальный пробел уже: конкретная маршрутизация HTML-пакета (origin, путь, cookie, grant) и репутационные границы домена.
2. **«Networkless ломает CDN» — завышение.** Серверный runtime воспроизводил React и Chart.js, если зависимости собраны заранее. Долю внешне зависимых входов не знает никто из нас. Удалённый pixel stream — риск, который нужно измерить, а не приговор.
3. **Об утечке я написал слишком легко.** Фраза «вопрос политики, а не свойство хостинга» неточна. В тесте Lanka RTCPeerConnection отправил STUN-пакеты из iframe, где parent, cookies, fetch и Worker были заблокированы. Значит, CSP и отдельный домен не доказывают отсутствие исходящей сети. Варианты (а) и (б) из первого раунда нельзя считать заранее прошедшими.
4. **«Поля без логики» — неверная формулировка.** Разделение «только владелец» и «явно публично» должно реально проверяться сервером. Один workspace по умолчанию без UI дешевле будущей миграции, возражение снимаю.
5. **Checksum не заменяет проверку содержимого.** Finalize должен проверять именно итоговые байты: тип, пути внутри архива, полноту пакета и права на момент finalize. Только после этого выдаются read grant и квитанция «готово».

## Решения

| # | Решение | Статус |

| 1 | Первый срез — сценарий A, то есть ограниченный допущенный preview. B — отдельная ставка. Старые M1+M2 не блокируют первый сигнал от пользователей. Трассировка на 195 строк заморожена как справочная база. Активная очередь — короткая спецификация R0 | Согласовано |
| 2 | Живая ссылка ведёт на указатель `publishedRevision`. Автор переключает его явным действием «Обновить по ссылке» после preview, проверки и политики; сохранение внешний результат не меняет. Pinned-ссылка и официальный выпуск закреплены на точной ревизии. Выданная сессия просмотра остаётся на одной ревизии. Права, срок и отзыв проверяются заново | Согласовано |
| 3 | Модель данных: tenant плюс workspace по умолчанию без UI. Папки без собственных прав. «Только владелец» и «явно публично» проверяются сервером. Классификация, наследование прав и корпоративный UI отложены | Согласовано |

Замеры на реальном корпусе: верность отрисовки, первый кадр, доступность, стоимость. Итог — выбор профиля или честное сужение формата | Эксперимент |

## Ядро R0

**Задача.** HTML или файл, полученный от агента, сохраняется на личной полке и открывается по ссылке так, как задумал автор.

**Действия:**
1. Принести: .html, ZIP, вставленный код; PDF и изображения как обычные файлы.
2. Открыть в профиле, который прошёл эксперимент 5.
3. Поделиться: «только я» или «по ссылке»; отозвать.
4. «Обновить по ссылке» из истории версий.
5. Папки, недавние работы, поиск по названию, мягкое удаление.

**Фундамент:**
- PostgreSQL и S3-совместимое хранилище;
- tenant и workspace по умолчанию; владеющий tenant отделён от `createdBy`;
- неизменяемые ревизии, идемпотентные мутации, квитанции;
- `actor_type` и таблица аудита;
- личный вход до создания публичной ссылки;
- лимиты и квоты;
- backup и restore для БД и объектов.

**Рядом, но не блокирует выпуск:** «Сохранить себе» у получателя — гипотеза распространения, записана в R1 с метрикой. MCP save/read начинается после стабилизации контракта ревизий.

## Пределы обещаний R0

- **«Любой HTML».** Не обещаем. Поддерживается только тот формат и профиль, который прошёл эксперимент 5, и это прямо написано на лендинге.
- **Отсутствие исходящей сети.** Не заявляем для профиля, который не прошёл строгий критерий (ii).
- **Отзыв.** Запрещает новые grant и работает в пределах объявленного TTL. Уже скачанные байты не удаляет.
- **Правка.** Нет правки произвольного HTML, кроме новой версии. Нет рецепт-редактора, комментариев, запуска агентов из UI.
- **Корпоративный уровень.** Нет SSO, классификации, утверждений. Внутреннюю установку R0 не называем готовой для компании.
- **Загрузка.** Нет multipart и возобновления после перезагрузки страницы.

## Разногласие, которое остаётся

**Не согласен, что «приватно» автоматически требует строгого отсутствия исходящей сети, а без этого остаются только публичный профиль или сужение формата.**

1. **Кого защищает строгий профиль.** Он нужен, когда недоверенный код получает данные, которые зритель или организация ему не доверяли. Если владелец смотрит свой приватный HTML, это по угрозам близко к открытию скачанного файла у себя в браузере, где сеть полностью доступна. Получатель по ссылке находится примерно в том же положении, что получатель файла по почте. Это моя аналогия, не проверенный факт.
2. **Главное: вилка «строго или публично» толкает к худшему.** Если приватная работа отрисовывается хуже или дороже, чем публичная, люди будут публиковать работы ради верного показа. Для приватности это хуже, чем приватный просмотр в браузере с явным предупреждением.

**Что рекомендую.** Для личного приватного профиля:
- исполнение в браузере с изоляцией от учётных данных приложения и других работ, то есть критерий (i);
- никакого обещания no-egress;
- видимая пометка «эта работа может обращаться в сеть, получатель может раскрыть свой IP».

Строгий профиль становится обязательным по политике организации и доступен как опция. Прежний тест Lanka не обхожу: он как раз доказывает, что без строгого профиля no-egress обещать нельзя.

**Это меняет формулировку обещания безопасности, поэтому решает владелец, а не мы с Codex.** Я изменю позицию, если эксперимент 5 покажет, что строгий профиль даёт сопоставимые верность, первый кадр и доступность при приемлемой стоимости. Тогда строгий профиль по умолчанию для всего приватного становится разумным.
