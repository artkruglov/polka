# Стартовая коллекция

Цель: посетитель сразу открывает несколько полезных красивых артефактов. Наполняем продукт содержанием, а не имитацией популярности.

Текущие 24 вымышленных автора — UI-fixtures. В новом каталоге 11 старых интерактивных примеров, отдельные сон/бюджет и 11 общих тематических графиков. Последние не считать готовыми исследованиями; либо заменить содержимое, либо убрать из стартовой публичной подборки.

## Набор beta

12–20 законченных артефактов, 4–6 тем, по 2–4 материала: путешествия/финансы, обучение/дети, данные/исследования, личные планы, творческие прототипы. Не менее пяти разных взаимодействий: расчёт, фильтр, шкала времени, слайды, checklist. Для здоровья — образовательные демо без реальных персональных данных и выдуманных медицинских выводов. Каждый материал имеет автора/редакцию, source, license/permission, краткую задачу, ключевое действие и проверенный mobile preview.

Три допустимые линии наполнения:

1. Оригинальные редакционные материалы Полки, собранные агентами; подписаны «Редакция Полки».
2. Материалы реальных авторов, которые явно разрешили размещение; атрибуция, точная лицензия и возможность снятия.
3. Вымышленные профили для дизайн-демо, с постоянной пометкой «Демо-автор» и исключением из реальных показателей. Не создавать фальшивые отзывы, лайки и историю использования.

Обнаруженный в X/Telegram/GitHub пример можно изучить. Публичный URL не означает разрешение копировать код, фото, текст и выдавать за другого автора. Нет явных прав — карточка ссылки или новая самостоятельная реализация задачи с собственными текстом, данными и визуалом; не маскировка копии под «синтез».

## Процесс

Кандидат → проверка источника/прав → локальный bundle без tracking/secrets → isolation/runtime check → mobile/content review → редакционное описание → публикация конкретной версии → периодическая проверка/снятие. Не выполнять скачанный код в доверенной среде. Сохранённый интерактивный HTML независим от исходного сервиса; внешняя ссылка в подборке честно обозначается как внешняя.

Research запускается отдельно по [готовому промпту](research/COLD_START_PROMPT.md). В этом проходе чужие материалы не собирались, согласия авторов не запрашивались, аккаунты и публикации не создавались.

## Проверенные кандидаты и следующий выпуск

[Аудит стартовой коллекции](reviews/2026-09-20-editorial/README.md) сопоставляет12 разных сценариев с текущими исходниками и конкретными пробелами. На момент аудита имелись один содержательный bundle и20 маленьких fixtures пяти семейств; это не12–20 готовых материалов. Аудит задаёт три независимых пакета по4 оригинала, которые принимаются через capture/runtime/mobile перед включением в витрину.

## Контракт интеграции редакционного каталога — ещё не реализован

Каталог — явный allowlist принятых immutable публикаций, а не выборка всех shares и не новый публичный actor. Первый выпуск включает восемь локально принятых оригиналов: fractions v2, city-observation, week-allocation v2, data-literacy, packing-checklist, contrast-explorer, meal-plan и sorting-explainer; [runtime evidence](reviews/2026-09-21-editorial-runtime/README.md) фиксирует проверки. Наличие других файлов в content/editorial само по себе не означает приёмку. Запись содержит slug, title/topic/task/action, автора «Редакция Полки», source path и commit/hash, Apache-2.0/notices, evidence и фактическую дату включения. Внутренний binding фиксирует tenant/artifact/revision, original manifest/hash и точные ready derivative id/hash/profile/builder; для single HTML без производного — original revision/hash. Capture/prepare выполняет авторизованный редакционный tenant через существующие services. Публикация — отдельное явное операторское действие с проверкой hashes и созданием специально предназначенной для каталога share. Тестовые unlisted shares и токены из evidence не становятся публичными автоматически; публичное чтение не выдаёт посетителю owner/service actor и не принимает произвольный artifactId.

Сервер отдаёт только публичную проекцию allowlist: описание, лицензию, slug и намеренно опубликованный recipient URL. При чтении проверяются текущие ограничения tenant/account/artifact/share/revision/derivative; недоступная, истёкшая или отозванная публикация исчезает, прямой recipient URL продолжает закрывать доступ. Просмотр использует существующие /s#token и recipient grant/viewer, без исполнения HTML на app origin; скачивание оригинала использует точный existing recipient export, не подменяя оригинал производным. Изменение работы не перемещает binding: новая версия требует нового принятия и явной публикации, чтение не продлевает expiry. Реальный маршрут /discover ведёт в Explore2026: его карточки/detail должны перейти с names[]/ArtifactPreview/community fixtures на catalog DTO; PublicGallery либо использует тот же источник, либо остаётся отдельным явно обозначенным demo. Вымышленные авторы, даты и показатели популярности не переносятся. Приёмка интеграции: восемь карточек с точными originals, работающие recipient/export, отсутствие подмены pinned версии, закрытие карточки и старого URL после revoke/trash/expiry, отсутствие private/test artifacts в listing. Это контракт локальной интеграции: каталог ещё не подключён, цель 12–20 материалов и hosted runtime остаются открыты.

### Следующий серверный пакет Sol: DB allowlist и явное включение

Хранение — таблица `editorial_publications`, а не committed список bearer URLs. Репозиторий хранит только проверяемые редакционные metadata и source/evidence; реальные UUID/bindings принимает операторский CLI. Общая pure schema/type живёт в `packages/editorial.ts` (Luna), не импортирует DB/config и сама ничего не публикует. Не добавлять seed при старте сервера, обход auth или публичный mutation endpoint. В pure контракте `editorialPublicationManifestSchema.public` содержит только редакционные metadata, без `publishedAt` и `recipientUrl`; strict operator input отклоняет эти серверные поля. Отдельный public response тип расширяет metadata датой DB и URL, который сервер вычисляет после проверок. `binding.manifestSha256` должен точно совпадать с `runtimeProof.originalManifestSha256`, включая null; derivative требует manifest, но manifest не требует derivative: существующий `createSingleHtmlRevisionManifest` сохраняет manifest также у single HTML. StorageKind определяется реальной revision в DB, а не наличием manifest. `source.commit` допускает null при точных hash/evidence.

- Миграция следующего свободного номера: `id uuid PRIMARY KEY`, `slug`, `tenant_id`, `artifact_id`, `revision_id`, `share_id UNIQUE`, nullable `derivative_id`, `source_sha256`, nullable `manifest_sha256`, nullable `derivative_sha256`, nullable `builder_version`/`runtime_profile`, `metadata jsonb`, `request_hash`, `published_at`, nullable `withdrawn_at`. Только ASCII slug `[a-z0-9]+(-[a-z0-9]+)*`, максимум80; hashes lowercase64hex. FK revision `(tenant_id,artifact_id,revision_id)` и derivative `(derivative_id,revision_id)` используют существующие constraints; share FK плюс сервисная проверка полного tenant/artifact/revision/derivative соответствия. Unique active slug `WHERE withdrawn_at IS NULL`; immutable binding/metadata/hash/date после INSERT, разрешено только одностороннее заполнение withdrawn_at. Никаких tokens/object keys/VersionIds в этой таблице: оригиналы и производные уже владеют storage references и квотами. Каталог не резервирует дополнительные bytes и не меняет GC.
- `scripts/editorial-publish.ts` имеет явные команды `publish` и `withdraw`, обязательный `--confirm-publication`, ожидаемый tenant/owner и JSON input с `publicationId`, metadata, exact binding/hashes и `expectedPublicationId` (null для отсутствующей активной публикации slug). Команда работает с доверенными операторскими DB credentials, не маскирует анонимного посетителя под владельца. Owner должен действительно владеть tenant и быть enabled; audit фиксирует этот явно выбранный owner, действие `editorial.published`/`editorial.withdrawn` и publication UUID. Dry validation не публикует; успешный stdout содержит UUID/slug/status, без bearer URL/token. `published_at` берётся из DB clock, не из input. Source hash обязателен; commit допускается null для ещё не закоммиченного оригинала с точным hash и evidence, не выдумывать revision Git.
- `publish` регистрирует **уже явно созданную для каталога** активную share; создание/подготовка работы и выдача этой share остаются существующим owner/MCP workflow. Не брать «последнюю share» и не искать candidates по всем tenant. Под tenant lock → затронутые artifacts в порядке UUID → shares → публикации проверить CAS slug, одинаковый tenant старой/новой публикации, active artifact, enabled owner, live gate, exact source manifest/hash и ready derivative текущего builder/profile; single HTML допускается только если текущий runtime действительно может его открыть. Сверить canonical manifest hash после JSONB. Для первого выпуска source.path указывает на оригинальный index.html, его SHA совпадает с entrypoint revision.sha256; bundle identity отдельно определяется manifestSha256. Запросы без принятого source/evidence или с несовпадением не создают row. Новый publication UUID повторяется только с тем же canonical request: exact retry возвращает прежний результат и текущее состояние доступности без повторной публикации; изменённый request —409. withdrawn/revoked запись retry не оживляет. Metadata request canonicalization должна переживать JSONB key ordering.
- Замена требует нового publication UUID и новой share с exact принятой версией; old row помечается withdrawn и old share отзывается в той же транзакции. Текущий `one_current_share` не позволяет две активные ссылки одного artifact: старую ссылку сначала явно отзывают обычным owner workflow, затем создают новую; временная недоступность допустима, скрытого продления/перепривязки нет. `withdraw` принимает publication UUID, проверяет tenant и атомарно помечает withdrawn + отзывает bound share; exact повтор безопасен. Общие share revoke действия выполняются в этой транзакции через небольшой InTransaction helper, без вложенных transaction и без новой бизнес-копии.

**Критическая совместимость с существующими shares.** `shares.ts:publishShareInTransaction` сейчас меняет revision/derivative существующей ссылки. Любая share, когда-либо зарегистрированная в editorial_publications, должна отклонять такое перемещение с409, включая withdrawn публикации: уже выданный `/s#token` не может начать показывать непринятый revision. Обычные owner shares сохраняют прежнее поведение. Revocation по-прежнему допустима и немедленно закрывает recipient/grants; restore artifact не восстанавливает публикацию. Это обязательный hook пакета, одной фильтрации списка недостаточно.

**Публичное чтение.** `GET /api/editorial` возвращает `{items:[...]}` с фиксированным пределом20; `GET /api/editorial/:slug` возвращает одну запись либо404. Оба endpoints без session, без выдачи actor; `Cache-Control: no-store`, DTO только редакционное описание, author/license/source attribution, slug, publication date и намеренно публичный `recipientUrl`. Исключить tenant/account IDs, connection, shareId, storage location, manifests, internal evidence paths и raw getArtifact. Общая query проверяет withdrawn, disabled owner, trash, share revoke/expiry, **равенство всех pinned IDs/hashes**, derivative ready/current builder/profile и runtime enablement. При изменившемся latest_revision старый принятый revision остаётся допустимым; брать latest запрещено. URL вычисляется существующим tokenFor только для прошедшей запись проверки, не логируется. Никаких бессрочных share и фонового автообновления TTL.

Принадлежащая каталогу share должна сохранять эти ограничения и при прямом recipient доступе. В текущих `app.ts` resolve/granted и recipient ветках `live-viewer.ts` disabled owner отдельно не проверяется; для editorial shares добавить небольшой общий SQL predicate текущей публикации/owner/binding, повторно используемый при resolve, grant read и viewer read/issuance. Обычные unlisted shares этим пакетом не переопределяются. Так скрытая карточка вследствие disabled owner или нарушения binding не оставляет обход через уже известный URL/grant. Withdrawal/replacement дополнительно используют обычный revoke, поэтому новые и ранее выданные grants закрываются существующим механизмом. Source/export остаются точной выгрузкой immutable original по recipient grants, а не новой копией derivative.

Файлы Sol: новая миграция + `packages/migrations.ts`/schema catalog restore drill, `apps/server/editorial.ts`, тонкие GET routes в app.ts, hooks shares.ts и recipient grants/live-viewer.ts, `scripts/editorial-publish.ts`, focused editorial integration tests. Luna независимо ведёт pure schema/metadata, затем frontend отдельным пакетом; UI и existing community fixtures серверный пакет не меняет. Проверки: explicit publish и exact retry без двойного audit; mismatch tenant/source/manifest/derivative/CAS отклоняется; private/test work отсутствует без publication; exact source export; no secrets в list/detail; republish bound share409, обычная share работает; revise не перемещает карточку; withdraw/revoke/expiry/trash/disabled закрывают list/detail/старый recipient/grant; restore не оживляет; новый UUID/share публикуется явно; ready false/unsupported никогда не выдаётся как интерактивная публикация. Эти тесты и локальный browser flow не доказывают hosted acceptance и не заменяют оставшиеся материалы до12–20.
