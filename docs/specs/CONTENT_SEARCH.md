# Поиск по тексту работ

> **Статус:** в коде с 25.09.2026, миграция 040; на polochka.app не выложено, после выкладки — `npm run search:backfill`. Первый пункт пакета для корпоративного пилота ([roadmap](../roadmap.md), этап 6).

Поиск на полке и в `polka_list` находит работу не только по названию, но и по её тексту. В выдаче есть фрагмент текста с найденными словами, поэтому и человеку, и агенту видно, почему работа попала в результаты. Агент может найти нужный отчёт по содержанию и продолжить его: `polka_list` → `polka_read_source` → `polka_revise`.

## Что индексируется

Индексируется только последняя версия работы. Для каждой работы хранится одна строка `artifact_search`: версия, текст до 60 000 символов и `tsvector` по конфигурации `russian`. В этой конфигурации русские слова приводятся к основе, латиница — английским стеммером.

| Тип работы | Откуда текст |
|---|---|
| HTML-страница | Видимый текст из того же разбора parse5, что определяет профиль и ищет фишинг (`inspectHtml`, опция `text`). Без `<script>`, `<style>`, `<template>` и текста, скрытого атрибутом `hidden` или CSS |
| Пакет (React/JSX от агента, несколько файлов) | Видимый текст входной страницы, текст JSX и строки скриптов, похожие на фразы (есть кириллица или несколько слов), — из того же прохода `scriptStrings`, что ищет фишинг |
| Текст | Сам текст |
| Сохранённая ссылка | Название, адрес и заметка (`linkText`) |
| Изображение | Не индексируется |

Страницу, которую не удалось прочитать за отведённое время (`UNREAD`), не индексируем. Её по-прежнему находит поиск по названию.

## Когда

- **При сохранении** — в той же транзакции, что и новая версия: в `finalizeUploadInTransaction` и `finalizeBundleUploadInTransaction`. Через них проходят все пути: веб, HTTP API, MCP, правки агента, импорт. Новая версия без текста удаляет строку предыдущей.
- **Уже сохранённые работы** заполняет `npm run search:backfill`. Скрипт идёт по последним версиям, читает байты из S3 и пишет строку, если её нет или она относится к старой версии. Повторный запуск безопасен.

## Поиск

Запрос разбивается на слова (буквы и цифры, до 8 слов), каждое ищется как префикс: `скид` находит «скидки». Все слова должны встретиться. Работа попадает в выдачу, если совпало название (`ILIKE`, как раньше) или текст. Порядок прежний: по времени изменения. Постраничная навигация не меняется.

Фрагмент (`ts_headline`, до 24 слов) возвращается только при совпадении в тексте. Найденные слова обрамлены символами U+E000 и U+E001: веб показывает их как `<mark>`, агент получает строку `snippet` с «…» вместо маркеров. Эти символы вычищаются из текста при индексации.

- `GET /api/artifacts?q=` — у элемента поле `snippet`.
- `polka_list {query}` — у элемента поле `snippet`, описание инструмента говорит, что поиск идёт по названию и тексту.

## Приватность и жизненный цикл

- **Где хранится.** Текст лежит в базе рядом с работой, а не в отдельном поисковом сервисе. Наружу он не уходит.
- **Кто видит.** Поиск видит только владелец и его агенты — тот же `tenant_id`, что и у полки. Шаблоны библиотек в эту версию не входят.
- **Удаление.** `artifact_search` ссылается на `artifacts` и `revisions` с `ON DELETE CASCADE`. Удаление аккаунта, очистка временной полки и перенос при слиянии аккаунтов (у строки нет `tenant_id`) не требуют отдельного кода.
- **Корзина.** Работа в корзине не ищется, как и раньше: условие `trashed_at IS NULL`.
- **Модерация.** Текст версии с активной блокировкой (`moderation_blocks.released_at IS NULL`) не участвует в поиске и не попадает во фрагмент. При окончательном удалении содержимого (`purgeBlock`) строка удаляется.

## Ограничения этой версии

- Нет сортировки по релевантности и нет семантического поиска. Для своей установки его можно добавить позже на локальной модели.
- Не ищутся библиотеки шаблонов и чужие работы. Командные полки — следующий этап пилота.
- Порядок слов и точные фразы не учитываются.
