## Результат для сотрудника

«У меня уже есть задача в чате. Найди наш шаблон предложения клиенту, используй его оформление и приложенный бриф». Агент находит разрешённый выпуск, читает исходники и правила, уточняет только недостающие данные. Пользователю не нужно повторять задачу в Полке. Альтернатива — открыть библиотеку, скопировать контекст и приложить пакет.

Не гарантируем воспроизведение корпоративного оформления одним prompt: в пакете должны быть настоящие HTML/CSS, доступные шрифты и изображения, пример и правила. Если сохранён только PDF или картинка, это визуальный ориентир, а не редактируемая тема. Создание происходит в агенте; Полка не вводит новый DSL презентаций или встроенный чат.

## Истории и критерии

| Роль и задача | Путь | Проверка результата |
|---|---|---|
| Куратор хочет дать команде утверждённое оформление | Сохранить материал → закрепить версию и правила → добавить в библиотеку | Все сотрудники видят один точный выпуск; личный материал не становится публичным |
| Сотрудник готовит предложение | Шаблоны → поиск «предложение» → контекст → текущий чат | Нет обязательного задания; пакет содержит исходники, правила и revisionId |
| Дизайнер использует только стиль | «Взять оформление» | Инструкция явно отделяет стиль от фактов и структуры |
| Руководитель соединяет несколько источников | Копирует несколько блоков в существующий чат | Идентификаторы материалов не смешиваются; нет автоматически созданных поручений |
| Агент сам находит шаблон | MCP list_templates с библиотекой и поиском → read_source | Та же версия и права, что в UI; source:read обязателен |
| Сотрудник без MCP | Скачать пакет или отдельные файлы | Реальные байты, manifest и правила; пакет не выдаётся за автоматическую передачу агенту |
| Куратор обновляет стандарт | Закрепить новый выпуск → заменить текущий в библиотеке | Новые запросы выбирают новый выпуск; прежние ссылки не подменяются другой версией |
| Администратор исключает сотрудника | Участники → отозвать доступ | UI, ZIP, отдельные файлы и новый MCP-запрос больше не читают библиотеку |
| Куратор отзывает ошибочный выпуск | Отозвать выпуск с причиной | Он исчезает из поиска и перестаёт читаться; другие личные материалы владельца недоступны всегда |

## Модель доступа

Индивидуальный аккаунт и индивидуальное подключение агента обязательны. Не менять tenant сотрудника на tenant владельца, не передавать общий токен, не открывать исходники через публичный preview.

| Операция | Читатель | Куратор | Администратор |
|---|---|---|---|
| Найти, просмотреть, скачать опубликованный выпуск | Да | Да | Да |
| Читать его через свой агент с source:read | Да | Да | Да |
| Публиковать свой разрешённый материал в библиотеку | Нет | Да | Да |
| Обновлять/отзывать выпуск библиотеки | Нет | Да | Да |
| Приглашать, исключать, менять роли | Нет | Нет | Да |
| Читать личные неопубликованные исходники другого участника | Нет | Нет | Нет |

Публичная ссылка, membership и source:read — разные основания. Для корпоративного чтения нужны активные membership, публикация и аккаунт; для MCP дополнительно активное подключение и scope. Скачанная копия не может быть отозвана. Домен почты сам по себе доступа не даёт. Исключение — настройка оператора `ORG_DOMAINS` / `OIDC_ORG_LIBRARY` ([SIGN_IN_PROVIDERS.md](SIGN_IN_PROVIDERS.md), раздел 2): при входе через поставщика с подтверждённой почтой домена человек становится читателем или куратором заданной библиотеки. Исключённого администратором это не возвращает.

## Хранение и архитектурная граница

Существующие artifacts/revisions/template_releases, хранилище, checksum-проверка, ZIP и sandbox сохраняются. Нужен отдельный модуль библиотеки, а не расширение всех owner-операций на чужие tenant.

Предлагаемые сущности:

- `template_libraries`: id, название, создатель, состояние. В первом срезе одна самостоятельная библиотека команды; не выдавать её за полную организационную модель всего продукта.
- `template_library_members`: library_id, account_id, role, состояние, время отзыва; уникальность пары. Активные роли reader/curator/admin.
- `template_library_invites`: library_id, подтверждаемый email, роль, hash одноразового токена, expires_at, accepted_at/revoked_at. Сам токен не хранить и не писать в лог. Принятие только аккаунтом с подтверждённой совпадающей почтой. Не отправлять реальные приглашения при тестировании.
- `template_library_publications`: library_id, release_id, publisher_id, published_at, withdrawn_at, причина. Ссылка на immutable выпуск; новая публикация не изменяет прежние правила или байты.
- `template_library_events`: актор, операция, библиотека, целевой id и время; без содержимого документов и секретов. Срок хранения и удаление персональных данных согласовать с существующим account-purge.

На первом этапе публикация ссылается на исходную ревизию. Удаление/корзина/блокировка её владельца должны закрывать библиотечное чтение. Это явно показать куратору. Независимое владение материалами организации и перенос квот — отдельный этап, не делать скрытое копирование с неопределённым владельцем.

Проверка существующего purge обнаружила важную особенность: `terminal_erase_account_metadata` (миграция020) анонимизирует accounts и сохраняет accounts/tenants, а не удаляет их. Поэтому `ON DELETE CASCADE` новых таблиц сам по себе не обеспечивает очистку членства и связанных метаданных. До внедрения библиотеки на рабочую базу нужны явная интеграция terminal purge, тест удаления участника без потери чужой библиотеки и политика передачи последнего администратора. Исходники удаляемого владельца должны стать недоступны сразу после блокировки, не дожидаясь фоновой очистки. Этот gate нельзя заменить тестом физического DELETE аккаунта.

Интеграция terminal purge добавлена в миграцию023 и проверена на изолированной установке с отдельными runtime/purge/restore ролями. При завершении удаления членство убирается, created_by/publisher_id очищаются; библиотека и исходники коллег сохраняются. Библиотека, теряющая последнего активного администратора, архивируется; при наличии другого администратора остаётся активной. Это не перенос прав на произвольного читателя. Содержимое библиотеки коллег не считается личными данными удаляемого аккаунта только на основании его авторства названия — автоматическое стирание чужих материалов не выполняется.

Проверены реальные защищённые SQL-функции, смена фаз purge и сохранение чужой публикации; `/tmp/polka-library-purge-runtime-final.log` подтверждает schema23, точные роли, deny-проверки, restore/S3 и очистку синтетических ресурсов. Первоначальный прогон остановился на старых schema20-ограничениях worker-grants; ожидания обновлены до23 при сохранении прежних разрешений. Рабочие ресурсы не использовались, обновление рабочей базы и UI-приёмка не проводились.

Единая серверная `authorizeTemplateRevision(actor, revision, library)` разрешает только личное чтение или конкретную активную публикацию. Её используют context, package, file, preview и MCP. Функцию чтения проверенных байтов выделить из owner-only `readRevisionSource`; нельзя подставлять actor владельца ради обхода проверки.

Проверять права на каждый запрос. Отзыв membership/publication сериализовать с выдачей исходников через единый порядок транзакционных блокировок; описать точку линеаризации: уже разрешённую передачу байтов нельзя отозвать задним числом. Не кэшировать положительный ACL дольше запроса. Добавить тест конкурентного revoke/read и исключить взаимные блокировки встречных чтений.

## UI и MCP

В существующем AppShell: «Шаблоны» → личные / выбранная библиотека. Общие TextField, Button, Dialog, Badge; никаких новых независимых меню. Карточка: назначение, выпуск, куратор/библиотека, состав; основное действие — контекст для агента, второе — посмотреть пример. Экран просмотра библиотечного материала не открывает owner-only /works с последующей ошибкой.

Контекст содержит libraryId, точные artifactId/revisionId/releaseId и варианты доставки. При отказе доступа показывается причина без названия чужого документа. Подключение агента объясняет, какие библиотеки видит сам сотрудник; новый scope не раздаётся старым токенам автоматически.

Расширить существующий polka_list_templates параметром libraryId и фильтром назначения, сохранив личный режим по умолчанию. polka_read_source получает libraryId и проверяет тот же ACL. Полезный пример: «Найди шаблон предложения в библиотеке команды; прочитай его файлы; используй приложенный бриф. Если данных не хватает, спроси в этом чате». Публикация и сохранение результата не следуют автоматически из чтения шаблона.

## Последовательность исполнения

1. **Личный выбор:** поиск по названию/назначению, последний выпуск по умолчанию, явная история, одинаковый контракт UI/MCP. Реализовано; проверки описаны в AGENT_CONTEXT_TEMPLATES.
2. **Данные и ACL:** новая миграция, runtime grants, membership/publication service, единый авторизатор исходников. Основа schema22 и read-authorizer реализована и проверена под runtime-role; рабочая база не обновлялась. До UI — два аккаунта, соседняя библиотека, неизвестная revision, scope/revoke/disabled/trash, конкуренция, работа под runtime role. Следующий пакет: интеграция purge и подключение авторизатора к чтению байтов; backup/restore и schema-ожидания должны быть проверены в той же поставке.
3. **Участники:** создание библиотеки, проверяемые приглашения и роли. Не разрешать удалить последнего администратора без передачи роли. Существующий SMTP; для тестов только local mail. Блокировать истёкшие, повторные и адресованные другой почте приглашения.
4. **Публикация и использование:** выбор библиотеки, публикация конкретного выпуска с явным предупреждением о доступе к исходникам, отзыв, каталог/поиск, preview, context/ZIP/files/MCP. Не показывать неработающие кнопки корпоративного доступа до готовности сервера.
5. **Приёмка:** куратор публикует корпоративную презентацию; другой сотрудник находит её в UI и своим MCP; агент делает новую презентацию с другим содержанием; ручной осмотр типографики, ресурсов и отсутствия демонстрационных фактов. Повторить с ZIP без подключения. Отозвать сотрудника и проверить отказ всеми каналами. Desktop/mobile и воспроизводимые доказательства; симуляция ролей не заменяет этот прогон.

Не входит: SSO/SCIM, права всех документов компании, корпоративное юридическое владение файлами, встроенный редактор PowerPoint, сертификация стиля, универсальная совместимость с любым агентом. Это не отменённые требования, а следующие отдельные этапы.


## Следующий интерфейс управления по существующим API

Один пакет после MCP discovery, без новых моделей данных. В `/templates` оставить единый AppShell и выбор библиотеки.

- «Создать библиотеку»: только название, POST /api/template-libraries; после успеха выбрать новую библиотеку. Не запрашивать задачу для агента.
- Для выбранной библиотеки кнопка «Участники». Reader видит состав и роли; admin также создаёт приглашение с почтой, ролью и сроком, копирует полученную ссылку, меняет роли и отзывает доступ. Явно написать, что письмо автоматически не отправлено. Ошибку последнего администратора показывать как конкретное действие — сначала назначить другого.
- Список приглашений доступен admin. Для ожидающего приглашения — отзыв; для принятого — переход к участникам. Секрет доступен только сразу после создания; не обещать повторное получение ссылки из списка.
- «Добавить шаблон» для curator/admin: выбрать собственный закреплённый выпуск из личного каталога, показать название и версию перед POST publications. Не принимать произвольные artifactId или выдавать чужой материал за собственный.
- «Убрать из библиотеки» для curator/admin: указать причину, POST withdraw. Объяснить, что личный оригинал остаётся у владельца; скачанные копии не удаляются.
- Все запросы через общие API/helpers, pending/error/retry у каждого действия, обновление списка после мутации. Server ACL остаётся авторитетным при изменении роли в другой вкладке.
- В библиотеке должно быть видно ограничение владения: исходник принадлежит автору; его удаление или блокировка закрывает чтение. Не называть это независимым корпоративным хранилищем.

Приёмка: два отдельных аккаунта, admin создаёт библиотеку/приглашение/публикацию; reader принимает и читает точный контекст, не видит управляющие действия; отзыв закрывает следующий запрос. Проверить mobile390 и ошибки API. Предпросмотр материала реализуется отдельным пакетом через действующий изолированный viewer, не через HTML на app-origin.


## Контракт просмотра библиотечного шаблона

Проверка кода: `issueOwnerLiveView` требует сессию владельца source tenant, а `issueRecipientLiveView` — grant публичной/закрытой ссылки. Ни один из этих путей не представляет библиотечное членство; подставлять владельца или выпускать share ради просмотра нельзя. `LivePreview.tsx` уже использует отдельный VIEWER_ORIGIN, iframe sandbox=allow-scripts и no-referrer — эти свойства сохранить.

Следующий серверный пакет после UI управления:

1. Отдельный короткоживущий library-viewer grant (случайный token, хранить hash, срок не больше60 секунд и срока session), привязанный к session, library/publication/exact revision и текущей membership epoch. Не расширять существующий owner-grant до произвольного читателя.
2. Выдача grant через POST с exact publication/revision после `authorizeTemplateRevision` в свежей транзакции. Никакого изменения общего доступа. Готовый bundle derivative должен совпадать с manifest hash, builder version и runtime profile. Состояние «нужно подготовить просмотр» отличается от «нет прав».
3. Viewer GET повторно проверяет session, ту же membership epoch, active library/publication, source owner и отсутствие trash. Держать авторизацию до чтения pinned bytes по существующему library lock order. Отозванный член не получает доступ через старый grant после нового вступления. Уже загруженный iframe не может быть стёрт из памяти клиента; следующий запрос обязан быть отклонён.
4. Исходники и токен никогда не получают app-origin privileges. Viewer возвращает только готовые bytes через существующую CSP; сетевые ограничения не ослаблять.
5. Удаление session/account/membership/publication/revision очищает связанные grant; расширить isolated purge/restore coverage и reviewed migration guards. Не менять рабочую БД до приёмки интегрированного пакета.
6. В UI «Посмотреть материал» открывает общий диалог/страницу с названием, версией, библиотекой, viewer и «Скопировать для агента». Обязательны загрузка, отказ доступа, недоступный/неподготовленный preview, повтор; не оставлять кнопку, ведущую в owner-only `/works`. Для bundle без derivative предусмотреть авторизованную подготовку через существующий builder, а не неявное выполнение сырых файлов.

Проверки: member/outsider, mismatch revision/publication, revoked→rejoin старого grant, session expiry, source trash/disable, exact derivative, CSP и реальный iframe desktop/mobile. Дополнительный внешний релиз для этого не нужен.


### Подготовка интерактивного материала участником — текущий серверный этап

Реализация — отдельным пакетом; ниже критерии, не заявление о готовности.

- Сборщик получает явный sourceTenantId и авторизованный reader; identity участника не заменяется владельцем. Квоты, резерв и immutable derivative принадлежат исходному tenant.
- Библиотека, публикация, revision и membership epoch проверяются перед чтением и при финализации. Отзыв во время worker не разрешает получить результат через старое членство.
- Режим блокировки для записи выбирается до получения SHARE locks; параллельные сборки и owner/library операции не должны создавать циклы upgrade locks.
- Переиспользовать ресурсные лимиты builder и штатную maintenance-очистку expired pending/orphan bytes (существующее доказательство в tests/bundle-runtime.test.ts). Без cleanup bypass после отзыва; явно указать зависимость от maintenance.
- Приёмка: настоящая сборка чужого опубликованного bundle участником → существующий library viewer; outsider/mismatch/revoke deny; owner regression, concurrent preparation и quota/residue recovery. Только isolated tests, без рабочей миграции.
- UI-кнопка подготовки — следующий пакет после серверного контракта; текущий preparation-required текст не считать финальным пользовательским сценарием.


### Журнал библиотеки — согласованный серверный пакет

Реализуется schema26, ещё не принятую на рабочей установке: отдельные события library/actor/action/typed target/oldRole/newRole/time, вставка атомарно с успешной мутацией, без дублей no-op/replay. Без email/token/имён/исходников/reason free text. Чтение active-admin-only с курсором before и ограниченным limit.

Runtime имеет SELECT/INSERT, не UPDATE/DELETE.
