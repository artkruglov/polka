# Расширения открытого ядра

> **Статус:** в коде с 26.09.2026; `content`, `auditFeed` и печать в PDF — с 0.10.0; вход и учётные записи расширения (`accounts`, `teamShelves`, `signInPaths`, `signInMethods`, `policies.signIn`) — после 0.14.0. Точки расширения — часть открытого ядра (AGPL-3.0). Ими может пользоваться любое расширение, в том числе коммерческая редакция для организаций.

Полка — одно приложение для облака и для своей установки. Расширение добавляет к нему правила и функции, не меняя ядро. Без расширений ядро работает так же, как без этой спецификации: все точки пустые.

## Подключение

- `POLKA_EXTENSIONS` — имена пакетов или пути к модулям через запятую. Пусто — только ядро.
- Модуль экспортирует по умолчанию объект `PolkaExtension` (`packages/extension-api/index.ts`) с полем `name`: латиница, цифры и дефис, до 31 знака.
- Ядро загружает расширения один раз при старте и регистрирует их после своих маршрутов.

## Точки расширения

| Точка | Когда вызывается | Что может |
|---|---|---|
| `register(app, context)` | При старте, после маршрутов ядра | Свои маршруты под `/api/ext/<name>/` и фоновая работа. `context.identity` — вход и выбранная полка, как у ядра; `context.transaction` — транзакция с ролью приложения; `context.settings.teamShelvesScope` и `context.companyAdmin(accountId)` — администратор ли аккаунт компании и какой организации (`{ organisationId }`, `null` — не администратор; `organisationId: null` — вся установка, [TEAM_SHELVES](TEAM_SHELVES.md#организации-в-облаке-миграция-070)) |
| `policies.linkIssue` | Внутри транзакции выпуска ссылки и её перевода на новую версию, до записи | Запретить с понятным человеку сообщением: 403 |
| `policies.linkOpen` | Внутри транзакции открытия ссылки получателем | Запретить (403) или потребовать вход в эту установку (401 с `reason: "sign_in_required"`). Страница получателя тогда предлагает войти в новой вкладке и открыть снова: токен ссылки не попадает в адрес |
| `policies.agentScope` | При каждом действии агента | Ограничить подключение папками полки (`{ folderIds }`), `apps/server/agent-scope.ts`. Работы вне их для агента «не найдены». Новая работа без папки сохраняется в них. Перенести работу наружу, создать, переименовать или удалить папку агент не может. Токен загрузки проекта действует как подключение, которое его выдало |
| `policies.sessionDelete` | Внутри транзакции, когда человек удаляет свою сессию агента | Запретить с понятным человеку сообщением: 403 с `reason: "session_policy"` (например, компания хранит сессии по своему сроку). Стирание аккаунта не спрашивается |
| `onEvent` | После фиксации транзакции | `revision.saved`, `share.created`, `share.revoked`, `member.revoked`. Для уведомлений, где потеря не страшна. Доставка «не больше одного раза»: событие не хранится и теряется при перезапуске или падении процесса; повтор идемпотентного запроса может прислать его снова. Ошибка расширения пишется в лог и не ломает ядро. Для работы, которую нельзя потерять, — `context.auditFeed` |
| `context.content` | Когда расширению нужно содержимое | `revision(tenantId, revisionId)` — версия любой полки установки: работа, полка, папка, номер, дата, файлы (`path`, `mime`, `size`, `sha256`) и `unavailable`. `openFile(…, index)` — файл потоком; поток сверяется с записью версии и обрывается ошибкой в конце при расхождении, видео тоже. Версию, которую модератор изолировал или стёр, ядро называет (`unavailable: "blocked" \| "removed"`), но не отдаёт; работу, удалённую навсегда, не находит. `pdf(…)` — то, что увидит получатель, напечатанное на A4 рендерером (`POST /pdf`), или причина, почему печати нет; `null`, если рендерер не настроен |
| `context.sessions` | Когда расширению нужны сессии агентов | Чтение сессий всех людей установки, то же, что видит владелец на своих страницах ([AGENT_SESSIONS](AGENT_SESSIONS.md)): `list(selection, query)`, `get(id, selection)`, `stats(selection, {days})` (плюс `people` — итоги по людям, и число людей у отпечатков, адресов, MCP-серверов), `transcript(id, {offset, limit})`, `transcriptFile(id)`. `selection.accounts` ограничивает людьми. Значений секретов здесь нет: их заменили ещё на машинах. Просмотр расшифровки расширение записывает в свой журнал само. Нет сессии — 404 ядра |
| `machinePaths` и `context.agent(req, reply, scope)` | Маршруты для машин: агентов, сборщиков телеметрии, каталогов сотрудников (SCIM) | `machinePaths` — точные адреса под `/api/ext/<name>/`, которые вызывают не из браузера, а с токеном (`Authorization: Bearer`): агента или своим токеном расширения, например каталога SCIM. Адрес, который кончается на `/*`, покрывает всё под ним (`/api/ext/<name>/scim/v2/*` — и `/Users/{id}`). Ядро не требует для них заголовка `Origin` своей страницы; адрес вне своего префикса не даёт расширению загрузиться. Обработчик проверяет токен через `context.agent(req, reply, scope)` — так же, как маршруты `/api/v1` ядра: 401 без действующего токена, 403 без разрешения `scope`, 429 сверх частоты подключения; возвращает `{ connectionId, accountId, tenantId }`. `context.identity` на таких адресах отвечает 403: без проверки `Origin` вход по cookie можно было бы подделать |
| `context.redact(text)` | Когда на сервер приходит текст, который не скрыли на машине | Тот же поиск секретов, что у `polka-sessions.mjs` ([AGENT_SESSIONS](AGENT_SESSIONS.md)): возвращает `{ text, secrets }`, где в `text` секреты заменены метками `[REDACTED:<тип>:<отпечаток>]`, а `secrets` — `{ type, fingerprint }` каждого найденного, без значений. Отпечаток считается ключом установки (выведен из `LINK_KEY`, как при `AGENT_SESSION_FINGERPRINTS=installation`): с этой настройкой он совпадает с отпечатком того же секрета в отправленных сессиях, с ключами полок (по умолчанию) — нет. Синхронно, без обращения к базе. Для телеметрии агентов (OTLP), команд и других строк, которые расширение хранит или показывает |
| `signInPaths` | Ответ сервиса входа компании приходит в браузере человека | Точные адреса под `/api/ext/<name>/`, куда страница поставщика входа отправляет браузер POST-запросом (SAML ACS). Ядро не требует для них `Origin` своей страницы; `context.identity` там отвечает 403. Обработчик сам проверяет ответ поставщика (подпись, получателя, срок, повтор) и входит через `context.accounts.startSession` |
| `signInMethods()` | При каждом `/api/capabilities` | Кнопки входа расширения на страницах входа ядра (`/signup`, `/login`) после кнопок поставщиков: `{ id, name, start }`, где `start` — GET-адрес расширения под `/api/ext/<name>/`; страница добавляет `next=<путь этой установки>`. Нет настроенного входа — пустой список, нет кнопки. Ошибка пишется в лог и не показывает кнопку. Неудачный вход расширение возвращает на `/signup?idp_error=sso` |
| `policies.signIn` | Перед входом ядра: перед отправкой кода на почту, при проверке кода, при входе по паролю и при возвращении от поставщика (Яндекс ID, VK ID, Google, OIDC) | Запретить с понятным человеку сообщением: 403 с `reason: "sign_in_policy"`. Получает способ, адрес (в нижнем регистре; у поставщика — только подтверждённый) и аккаунт, если он уже есть. Например, «почта домена компании входит только через её SSO». У поставщика человек видит общий текст (`idp_error=policy`): адрес возвращения не несёт сообщений. Привязка способа входа к своей полке и вход по ссылке агента не спрашиваются; вход самого расширения (`startSession`) — тоже |
| `context.accounts` | Вход и учёт сотрудников расширением: SSO, каталог SCIM | `get(id)`, `findByEmail(email)`. `provision({ email, name })` — аккаунт с этой почтой или новый с личной полкой: почта подтверждена, ограничения регистрации не действуют (компания заводит своих людей), логин `sso-<id>`; существующий возвращается как есть (`created: false`), отключённый тоже. `update(id, { email, name })` — почта другого аккаунта: 409. `deprovision(id, { reason })` — человек ушёл: аккаунт отключён, все сеансы закончены, все подключения агентов (токены и OAuth) отозваны, человек снят со всех полок отделов (`member.revoked` на каждую); ничего не удаляется, ссылки его личной полки не открываются, пока аккаунт отключён; в журнал — `account.deprovisioned`; повтор ничего не меняет. `reactivate(id)` — снять это отключение; аккаунт, который отключил оператор или модерация, остаётся отключённым (403, `reason: "operator_disabled"`); полки отделов не возвращаются — их возвращает каталог. `startSession(reply, accountId)` — сеанс ядра (cookie `polka_session`, 7 дней) человеку, которого расширение проверило; отключённому — 403. Соответствие внешних id и аккаунтов расширение хранит у себя |
| `context.teamShelves` | Группы каталога как полки отделов ([TEAM_SHELVES](TEAM_SHELVES.md)) | `list()`, `get(id)`, `create(name)` (без участников), `rename(id, name)`, `members(id)`, `setMember(id, accountId, role)` — добавить или сменить роль (`reader`, `author`, `curator`, `admin`; отключённый аккаунт — 409), `removeMember(id, accountId)`. Изменения пишутся в журнал полки без автора (`actor_id` пустой). Каталог — источник правды: `removeMember` снимает и последнего администратора, полку без администратора компания видит на своей странице и может её взять. При выключенных полках отделов — 404 |
| `context.auditFeed` | Опрос по своему курсору | Журнал действий всей установки (`audit_outbox`) в порядке фиксации: `read(cursor, {actions, limit})` и `head()`. Курсор расширение хранит в своей таблице: после перезапуска ничего не теряется, а транзакция, зафиксированная позже начатой раньше, не пропускается (то же правило, что у ленты агентов `GET /api/v1/events`). Стирание аккаунта оставляет в журнале одну строку `account.erased` (цель — id аккаунта, `payload` пустой): по ней расширение удаляет свои производные данные о человеке |

Если одну и ту же точку заняли несколько расширений, действует первый отказ.

## Часть расширения в интерфейсе

- **Скрипт.** Расширение указывает `web.script` — путь к одному ES-модулю. Ядро отдаёт его как `/ext/<name>.js` с того же адреса (CSP `script-src 'self'`) и называет расширения в `/api/capabilities` (`extensions`).
- **Подключение.** Страница, у которой есть место для расширений, подгружает модуль тегом `<script type="module">`. Модуль получает `window.__polkaHost` (`ExtensionHost`, `packages/contracts/extensions.ts`):
  - React приложения — второй копии нет;
  - элементы интерфейса: `Button`, `SelectField`, `TextField`, `Checkbox`, `Stack`, `Notice`, `ErrorNotice`, `Badge`, `Fine`;
  - `request` — клиент API с сессией и выбранной полкой;
  - `addSection(slot, …)`.
- **Места:**
  - `company-admin` — разделы на странице администратора компании;
  - `agent-connection` — под каждым действующим подключением на странице «Агенты». Раздел получает `connection`: `id`, `name`, `kind`, `shelf`.
  - `share-dialog` — в окне «Поделиться», над примечанием внизу: например, правила ссылок с этой полки. Раздел получает `artifact` (`id`, `title`, `revisionId`, `revisionNumber`), `shelf` (полка отдела или `null` — своя) и `link` (`status`, `expiresAt` или `null`). Решает, можно ли выпустить ссылку, по-прежнему `policies.linkIssue` на сервере; раздел только объясняет правила заранее.
- **Стили.** Своих стилей расширение не приносит, выглядит как остальная Полка.
- **Доверие.** Код модуля выполняется с правами приложения: подключать его может только оператор установки (`POLKA_EXTENSIONS`).

## Данные расширения

Расширение хранит свои таблицы в своей схеме PostgreSQL, например `polka_enterprise`. У него свои миграции и свой рецепт прав для роли приложения. Точный набор миграций ядра (`packages/migrations.ts`) и рецепты прав ядра (`deploy/*-grants.sql`) для расширения не меняются и проверяются как раньше.

## Коммерческая редакция

Коммерческая редакция для организаций — расширение `@polka/enterprise` из приватного репозитория. Она распространяется по договору и включается подписанным ключом лицензии.
- Без ключа не работает само расширение.
- Ядро работает всегда, и в облаке polochka.app работает только оно.

Что входит в редакцию — на странице [«Для компаний»](https://polochka.app/enterprise) и в [COMMERCIAL.md](../../COMMERCIAL.md).

Расширение — доверенный код в процессе ядра: `content`, `auditFeed` и `sessions` видят все полки установки. Подключает расширения только оператор.

Курсор `auditFeed` — номер транзакции PostgreSQL. Он переживает восстановление из физической копии и `pg_upgrade`, но не перенос логическим дампом в новый кластер: там номера начинаются заново, и новые строки окажутся «позади» сохранённого курсора. После такого переноса расширение должно начать с `head()`.

## Вход и учёт сотрудников (SSO, SCIM)

Протоколов входа и каталогов в ядре нет: SAML и SCIM — в коммерческой редакции. Ядро даёт только то, без чего расширению пришлось бы повторять его работу:
- адрес, куда поставщик возвращает браузер (`signInPaths`);
- кнопку входа (`signInMethods`);
- запрет своих способов входа (`policies.signIn`);
- заведение и отключение людей и состав полок отделов (`accounts`, `teamShelves`) теми же правилами, что у ядра: сеансы, отзыв агентов, журнал полки, событие `member.revoked`.

Миграций ядра для этого не нужно.

## Тесты

`tests/extension-content.test.ts` — `content` и `auditFeed`: файлы одиночной версии и проекта, заблокированная, в корзине и удалённая работа, поток, который не совпал с записью, журнал за поздно зафиксированной транзакцией, печать без рендерера. `/pdf` с настоящим Chromium — `npm run test:renderer-runtime`.

`tests/extension-accounts.test.ts` — вход и учёт: POST с чужим `Origin` на `signInPaths` даёт сеанс ядра, cookie там не читается, `/*` в `machinePaths`, кнопки в `/api/capabilities`, отказ кода и пароля для домена, полка отдела по каталогу, `deprovision` (сеансы, полки, событие, повтор), `reactivate` не снимает отключение оператора, неверные пути при загрузке.

`tests/extensions.test.ts`. Тестовое расширение:
- запрещает ссылки дольше 7 дней;
- требует вход получателя;
- получает события;
- добавляет свой маршрут;
- загружается по пути.
