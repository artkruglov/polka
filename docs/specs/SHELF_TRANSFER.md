# Перенос полки в свою установку

> **Статус:** в коде с 03.10.2026 (версия 0.9.0): `GET /api/v1/export`, `polka-export.mjs`, `npm run admin -- shelf import`, раздел «Перенести полку» в настройках. Закрывает требование R17 «Забрать данные и уйти» для всей полки.

## Зачем

Человек попробовал Полку на polochka.app, а работать дальше хочет на установке своей компании, или просто уходит. Работы должны переехать целиком: со всеми версиями, их номерами и датами, а не только с последним состоянием. Облако работает на открытом ядре, поэтому обе половины — выгрузка и импорт — тоже в ядре ([DECISIONS](DECISIONS.md), 03.10.2026).

## Что переносится

| Переносится | Не переносится |
|---|---|
| Все работы личной полки, включая корзину и сохранённые ссылки | Работы, удалённые навсегда |
| Все версии с исходными номерами, датами и файлами; у одиночной HTML-страницы — исходное происхождение (`provenance`) | Ссылки: их адреса и секреты привязаны к домену, на новом месте ссылки выпускают заново |
| Папки (по имени: одноимённая на новой полке используется) | Комментарии и реакции: их авторы — люди старой установки |
| Название, принятая версия (с датой отметки в журнале), «ответственный — я», дата изменения, время помещения в корзину | Подключения агентов, способы входа, полки отделов, библиотеки шаблонов |
| Карточка полки (если на новой полке её нет, или с `--replace-card`) | Обложки, поиск и интерактивные сборки — новая установка строит их сама |

Работа, у которой хоть одна версия заблокирована модератором (изолирована или стёрта), выгрузкой перечисляется, но её байты не отдаются, и импорт пропускает такую работу целиком, называя её в отчёте: дыра в нумерации версий хуже отсутствия работы.

## Выгрузка

Токен агента («Агенты» → токен) с правами `read` и `source:read`, на всю полку: токен, ограниченный папками (коммерческая редакция), и полка отдела получают `403`. Токен загрузки проекта не подходит (`401`), из браузера адрес не вызывается. После запроса на удаление аккаунта выгрузка не работает — поэтому раздел «Удалить полку» сначала отправляет к «Перенести полку».

- `GET /api/v1/export?cursor=&limit=` — опись страницами по id работы (до 50 работ, меньше, когда на странице набирается 1000 версий; работа всегда целиком). Формат `polka-shelf-export/1` ([контракт](../../packages/contracts/shelf-export.ts)): `source` (адрес, полка, почта, версия Полки), `shelf` (`cardMd`, `folders`), `items[]` с `revisions[]`, у каждой — `files[]` (`index, path, mime, size, sha256`) и `unavailable` (`blocked`/`removed`/`null`).
- `GET /api/v1/export/revisions/:revisionId/files/:index` — байты файла, `X-Polka-Sha256`. Работы из корзины тоже (обычный `/api/v1/works/...` их не видит). Лимит отдельный: 3000 файлов за 10 минут на подключение; опись идёт в общий лимит 120 запросов.
- `polka-export.mjs` (без зависимостей, Node 22+; `GET /api/v1/cli/polka-export.mjs` отдаёт его с адресом установки) пишет `polka-export.json` и `blobs/<sha256>`: каждый файл один раз, с потоковой проверкой суммы, через временный файл. Повторный запуск продолжает с места: готовые файлы проверяются и не скачиваются. `exportId` в `polka-export.json` сохраняется между запусками. Токен — только из `POLKA_TOKEN`; https обязателен, кроме localhost; перенаправление не выполняется (токен не уходит на другой адрес); имя файла на диске — только sha256, пути из манифеста на диск не попадают.

## Импорт

Команда оператора своей установки, под ролью приложения, как `account-merge`:

```sh
npm run admin -- shelf import --dir ./polka-export --account <логин|почта|id> [--dry-run] [--raise-quota] [--replace-card] [--json]
```

1. **Проверка** (то же, что `--dry-run`, до первой записи): формат, манифесты против их сумм, что эта установка примет запрос каждой версии (типы файлов, лимиты; иначе работа пропускается), номера версий подряд, каждый файл в `blobs/` по размеру и SHA-256, место (`quota_bytes` с учётом идущих загрузок; `--raise-quota` поднимает лимит полки до нужного), видео при выключенном `video_enabled`, не больше 100 папок, аккаунт действует и полка личная.
2. **Полка:** недостающие папки, карточка.
3. **Версии по порядку номеров** — обычным путём сохранения (`beginUpload…`/`beginBundleUpload…` и их `finalize…InTransaction`): фильтр содержимого, стоп-лист, лимиты, квота, поиск и журнал срабатывают как при новом сохранении. В той же транзакции, что сохранила версию: исходная дата `created_at`, у одиночной HTML-страницы — исходное `provenance` (сумма манифеста пересчитывается); номер сверяется с исходным.
4. **После последней версии работы:** название, папка, принятая версия (по номеру), ответственный, `updated_at`, корзина; отметка принятия пишется в журнал (`revision.accepted`) с исходным временем, поэтому [снимок полки](SHELF_SNAPSHOT.md) видит её тогда. В корзину работа уходит последней: в работу из корзины новые версии не сохраняются. Этот шаг выполняется один раз: в журнал пишется `artifact.imported` с `exportId`, и повторный запуск не трогает работу, которую владелец уже восстановил из корзины, переименовал или переложил.

**Повторный запуск.** Ключ загрузки версии — UUID из `exportId`, id исходной версии и номера попытки; сохранённая загрузка хранит квитанцию навсегда, поэтому второй запуск находит сделанное и продолжает после него, ничего не сохраняя дважды. Истёкшая загрузка (`410`) повторяется со следующим ключом. Серверной таблицы происхождения нет: миграция не нужна.

**Модерация новой установки.** Версия, которую фильтр содержимого при сохранении изолировал, сохраняется, но не открывается; отчёт называет такие версии у каждой работы («заблокировано модерацией этой установки: v2»), решение принимает модератор (`moderation.ts`). На проверке 06.10.2026 так изолированы две тестовые страницы с попытками выхода в сеть.

**Отказы по ходу.** Стоп-лист или другая ошибка сохранения у одной работы — работа в отчёте как пропущенная, остальные переносятся. Если до ошибки часть версий уже сохранилась, отчёт так и говорит («сохранено версий 2 из 3»); работа остаётся на полке как есть, без принятия и корзины. Если фильтр содержимого отключил аккаунт, импорт останавливается.

## Ограничения

- Журнал старой установки не переносится, кроме отметки принятия: события `revision.saved` получают время импорта, а снимок полки на дату до импорта берёт корзину из `trashed_at`.
- Аналитика новой установки считает импортированные версии сохранениями.
- Модерация новой установки ставит все версии в очередь проверки, как обычные сохранения.
- Полки отделов не выгружаются (только личная полка).
- Обложки появятся при первом показе; `npm run admin -- backfill covers` строит их заранее.
