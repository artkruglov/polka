# R17: удаление аккаунта — следующий ограниченный пакет

> **Статус:** контракт. Отзыв доступа реализован, выключен по умолчанию (`ACCOUNT_DELETION_ENABLED`) и не принят для hosted-установки. Очистка данных — отдельный purge worker, не принят и не подключён к установке.

Статус: revoke slice принят локально на schema16; полный purge/ledger/restore в разработке и **ещё не принят**. Основание — REQUIREMENTS R17 и ARCHITECTURE: один account владеет одним tenant, memberships отсутствуют. Trash/restore сохраняет источники и квоты; maintenance удаляет только временные данные. Ни один из этих механизмов не является удалением аккаунта. Пакет следует за серверным каталогом и использует уже принятые guard/adapters GC, без нового общего lifecycle engine.

### Разрешённый первый implementation slice

Первый backend пакет реализует marker, plan/CSRF/status receipt, атомарный revoke и shared active-owner gates; **без purge, ledger, UI и terminal publication DELETE**. `ACCOUNT_DELETION_ENABLED=false` по умолчанию; включение разрешено только HTTP loopback с HOST, совпадающим с APP_ORIGIN hostname. Явная политика: purge hours integer1..8760, backup days integer0..3650 и version. Plan/confirm при выключении —503; read-only status уже выданного receipt продолжает работать, неизвестный/некорректный capability —404. Ответ честно содержит `purgeAvailable:false` и `access_revoked_pending_purge`; `workingDataPolicyDeadline`/`backupRetentionPolicyDeadline` обозначают только объявленные цели политики, не наличие worker или доказанный срок очистки. Confirm рассчитывает их от durable requested_at; план показывает предварительный расчёт. До полного R17 нельзя включать функцию для реальных пользователей или объявлять аккаунт очищенным.

Plan TTL10min. Повтор POST подготовки атомарно заменяет ещё неподтверждённый план новым planId и новым status capability; старый confirm получает409. Это восстанавливает lost first response и не выдаёт confirmable plan без доступного клиенту capability. Подтверждённый receipt/capability никогда не ротируется. Shared service порядок tenant→account→connection; deletion не ждёт challenge row, удерживаемый email verifier. Маркер нельзя снять или совместить с повторным включением account. Проверки первого пакета выполняются только на созданных synthetic tenants; остальные разделы ниже описывают ещё не реализованное полное завершение R17.

## Результат и сроки

После подтверждённой транзакции запроса аккаунт больше не входит в систему, все его подключения/ссылки/grants закрыты, каталог его материалы не показывает. Оригиналы, версии, производные, pending uploads и локальная почта удаляются повторяемой фоновой очисткой. «Доступ закрыт», «рабочие данные очищены» и «срок хранения резервных копий истёк» — разные состояния. Уже скачанные получателями копии и уже доставленные браузеру bytes отозвать невозможно.

До включения функции оператор задаёт проверенные `ACCOUNT_PURGE_MAX_HOURS` и `BACKUP_RETENTION_MAX_DAYS` плюс версию политики; UI и receipt показывают абсолютные сроки, рассчитанные на момент запроса. Для установки без backups явно задаётся0, а не молчаливый default. В текущих docs фактические сроки и рабочий backup lifecycle не подтверждены: не подставлять выдуманные числа и не обещать фактическую очистку backups по одному таймеру. Просроченная очистка остаётся pending/failed и видна оператору; readiness процесса не выдаётся за соблюдение retention. В beta acceptance поставка должна доказать эти сроки и описать отдельно retention журналов/провайдерской почты.

## Service и durable receipt

Новая миграция после каталога добавляет account deletion marker (`deletion_requested_at`) и небольшую таблицу `account_deletions`: UUID, account/tenant UUID, state, requested/revoked/purged timestamps, policy snapshot/deadlines, hash случайного status capability, retry timestamps и короткий error enum. Никаких email, titles, bearer tokens, source bytes или provider exception text в receipt. Один незавершённый запрос на account. Marker необратим в этом пакете; `disabled=false` не разрешается, если marker уже установлен. Новые accounts всегда получают новые account/tenant UUID.

Минимальный web flow — подготовка и подтверждение. `POST /api/account/deletion-plan` под текущей session и Origin/CSRF создаёт либо возвращает план без удаления: количество работ/версий, размеры, сроки, одноразово выдаваемый32-byte status capability. Capability даёт только обезличенный статус; перед первым изменением UI успевает сохранить его для восстановления ответа. План имеет короткий TTL. `POST /api/account/deletion` принимает planId, ожидаемые account/tenant UUID и явное подтверждение; текущая owner session и проверенный session-bound CSRF обязательны. Не переиспользовать agent token как owner credential. В одной транзакции marker + revoke + durable receipt. Ответ202 содержит requestId, состояние и сроки, стирает session cookie. Потерянный ответ восстанавливается через read-only `POST /api/account/deletion-status` с capability в body, no-store/rate limit, без auth side effects; capability никогда не попадает в URL/log. Повтор подтверждения после отзыва session не создаёт новый запрос: UI читает receipt. Exact duplicate в ещё авторизованной гонке возвращает тот же request, без повторного audit; чужой planId —404.

Это UI-first пакет доставки, не правило human-only management. Автоматизация account deletion потребует отдельного явного `account_delete` scope/инструмента и тех же CAS/receipt/tenant правил; существующий `manage` (rename/move/trash/restore) и уже выданные tokens не расширять до удаления аккаунта автоматически. Export выбранной версии через нынешний exact export остаётся доступен **до** подтверждения; не обещать ещё не реализованный export всего аккаунта одним архивом.

## Немедленное закрытие и гонки

Новый `apps/server/account-deletion.ts` использует текущую DB transaction и порядок tenant → account → connections → uploads → artifacts → shares → derivatives (внутри набора UUID ascending). Если нужны email advisory locks, брать их до tenant; не брать одновременно блокирующие login_challenges после account — verifier сейчас начинает с challenge row. В request transaction: проверить ownership/plan/session/CSRF, установить disabled+marker, отозвать все agent_connections, закрыть **все** shares, удалить viewer_grants перед grants/sessions, удалить CSRF, abort все unfinalized uploads, истечь pending derivative attempts и закрыть editorial publications через общий catalogue helper. Один audit без PII. Не обходить immutable publication trigger прямым произвольным UPDATE; использовать принятый withdraw/revoke путь внутри этой транзакции, без вложенных transaction.

`identity()` и ServiceActor recheck уже учитывают disabled, но этого недостаточно для запроса с закэшированным Actor. Общие owner mutations в `artifacts.ts`, folder creation, metadata/trash/shares и build begin/nonready/ready/finalize обязаны под tenant lock повторно проверять marker/disabled **до** PUT и перед commit. Background worker после CPU не имеет права записывать blob или готовый результат удалённому tenant. Сохраняются текущие правила хранения tenant locks через S3 PUT до DB commit; удаление, получившее lock, видит предыдущую завершившуюся запись и включает её в purge. Late operations, получившие lock после marker, отклоняются. При необходимости вынести небольшой `lockActiveOwnerTenant(c, actor)` вместо копирования predicates; ServiceActor сохраняет tenant→connection binding/revoke.

Read/export/recipient grants после commit запроса должны перестать работать: старые sessions/grants удалены, shares revoked, account disabled/marker повторно проверяются в чувствительных read paths. В-flight чтение, уже получившее разрешение и bytes до commit, не считать отзывом доставленного содержимого. Новые login sessions/challenges после marker не должны становиться действительными: password login перед INSERT session повторно проверяет account под согласованным lock; email verify делает то же. Email start для disabled/deleting identity отвечает без раскрытия существования и не создаёт новый challenge. Старые challenges и local mail удаляются отдельно bounded batches; использовать существующий email cleanup helper, но добавить selection по deleting identity, а не только expiry.

## Очистка источников и metadata

Отдельный `scripts/account-purge.ts`/модуль вызывается существующим maintenance loop малыми порциями под тем же dedicated session advisory lock4388002, общими AbortSignal/deadlines и maxAttempts1 S3 adapters. Не запускать второй неконтролируемый pool/job daemon. Один batch — один deleting tenant, не более100 version deletes; повтор после частичного S3 результата безопасен. Перед S3 tenant lock+marker; всегда повторные checks до/после awaited I/O и SQL. Ошибка/abort не помечает completed; известный частичный результат добирается следующей итерацией.

Для удаления аккаунта список DB object references недостаточен: нужен **весь** exact prefix `${tenantUUID}/` в versioned bucket, включая все исторические Versions, DeleteMarkers, ready derivative versions, pending attempt leftovers и upload orphans. Prefix строится только из подтверждённого UUID row, не принимается строкой от клиента; каждый возвращённый key повторно проверяется на prefix с завершающим `/`. Соседний UUID, service canary и другой tenant недоступны. Удалять только явно перечисленный непустой VersionId, никогда latest/DeleteObject без VersionId. Для продолжения после удаления безопаснее заново читать первую страницу оставшихся versions, чем сохранять marker удалённого объекта. Успех требует полного нетранкированного пустого listing после последнего batch; пустой только filtered subset не доказательство. DB references сохраняются до подтверждения очистки tenant prefix, поэтому unknown S3 delete не теряет inventory. Late PUT после marker запрещён указанными service gates. S3 provider должен подтвердить подходящую consistency/version semantics в выбранной поставке; существующий synthetic MinIO не доказательство production.

После пустого prefix удалить tenant-specific metadata в FK порядке: viewer_grants/grants, share_reports, withdrawn editorial_publications (нужен narrowly scoped terminal DELETE path, не обход ready/publication UPDATE trigger), shares; agent_operations и audit_outbox перед agent_connections; upload_files→uploads; обнулить artifacts.latest_revision_id, удалить revision_files и revision_derivatives, revisions→artifacts→folders. Удалить sessions/CSRF, login challenges и их local files. Проверить всю фактическую схему на момент реализации, включая новую catalogue миграцию. Пакет не копирует/переносит blobs и не уменьшает квоты активного соседнего tenant.

Конкретная зависимость после schema15: `preserve_editorial_publication()` запрещает **любой DELETE**, а publication FK держат shares/revisions/derivatives. Поэтому нынешняя схема намеренно не позволяет выполнить описанный R17 purge без новой миграции; это не повод ослаблять каталог сейчас. R17 migration добавляет отдельный аудируемый erasure function/привилегию: под tenant/deletion-job locks проверяет disabled+необратимый marker, нужный job tenant и подтверждённое завершение blob purge, разрешает terminal DELETE только withdrawn publication этого tenant и фиксирует число удалённых rows в durable deletion receipt в той же транзакции. Обычный app/operator catalogue DELETE продолжает отклоняться. Если применяется SECURITY DEFINER, зафиксировать search_path, квалифицировать таблицы и отозвать PUBLIC execute; не использовать доступный всем session GUC как доказательство права, `DISABLE TRIGGER`, удаление FK или blanket CASCADE. Regression: обычный DELETE по-прежнему fails; erasure чужого/active tenant fails; подтверждённый job удаляет только свои publication metadata и освобождает FK; audit/receipt survives остальную очистку. До этой отдельной migration R17 нельзя помечать completed даже после пустого S3 prefix.

Вместо каскадного удаления account с FK оставить минимальные disabled tombstones account/tenant, пока receipt/erase ledger требуют идентичность: email/display_name/email_verified_at=NULL, name — уникальная непривязанная UUID метка, password hash — новый неизвестный случайный пароль, used/derivative_used_bytes=0; никаких оригинальных credential hashes, metadata, titles или manifests. Это явно описывается в retention, не называется отсутствием всех DB rows. Состояние purged выставляется только после удаления source prefix, metadata/PII и local mail. Email challenges с row locks очищать SKIP LOCKED; пока остались locked rows, anonymization не завершать. Email start/verify и final scrub должны согласовать email advisory lock, чтобы старый challenge не создал новый аккаунт после удаления email из tombstone; не держать challenge row wait под противоположным порядком locks. Глобальные login_limits не имеют account FK; не чистить чужие IP limits. Известные account-specific hash keys можно удалить явно, остальные истекают по текущему короткому TTL и не считаются content.

## Backups и восстановление

Текущий synthetic restore fail-closed отзывает sessions/agents/shares, но **не удаляет account/source из старой копии**. Нужен durable erasure ledger вне восстанавливаемого backup generation: account/tenant UUID, deletion timestamp, policy deadline и status, без email/bytes. Durable запись/публикация ledger должна быть подтверждена до объявления запроса полностью зарегистрированным для production retention; при сбое доступ остаётся закрытым, outbox повторяет запись, состояние честно pending. Для local synthetic — отдельный явно выделенный journal target, не source/target DB одного restore snapshot. Поставщик хранения ledger и предел его retention — входные оператора, не новый SaaS.

Restore перед открытием доступа сверяет ledger и повторно подавляет/очищает deleting tenants; отсутствие актуального ledger — fail-closed, а не восстановление удалённого аккаунта. Backups исчезают по реально настроенному retention; нельзя удалять общий backup немедленно ради одного tenant и ломать восстановление остальных. Status сообщает deadline политики, а подтверждение удаления backups допускает только проверенная provider/backup процедура. R17 production acceptance остаётся открытым без этой процедуры; синтетический тест может доказать применение ledger к старому snapshot, но не истечение облачных backup копий.


### External erasure ledger v1: точный контракт следующего pure-модуля

Статус: контракт, ещё не реализация. Namespace — постоянный UUID установки `ledgerId`, записанный также в backup descriptor; его нельзя генерировать заново при restore. Journal bucket/credentials выбирает оператор отдельно от content bucket. Объект имеет ключ `erasure/v1/{ledgerId}/{requestId}/{event}.json`, где event — `revoke` или `purged`. UUID принимаются только в lowercase canonical форме. Ключ выводится из валидированного record, не принимается как свободный путь.

Оба strict JSON record содержат **ровно** поля `schemaVersion:1`, `event`, `ledgerId`, `requestId`, `accountId`, `tenantId`, `requestedAt`, `revokedAt`, `policyVersion`, `workingDataPolicyDeadline`, `backupRetentionPolicyDeadline`. Policy version соответствует текущему regex `[A-Za-z0-9._-]{1,80}`. Все timestamps — существующая календарная UTC дата строго `YYYY-MM-DDTHH:mm:ss.sssZ` (round-trip через Date должен совпасть); `requestedAt <= revokedAt`, оба deadline >= requestedAt. Значения один раз снимаются с durable DB receipt с точностью до миллисекунд и сохраняются как payload: retry не пересчитывает часы/политику. Просроченный фактический purge допустим: это не ошибка формата и не основание подделать deadline.

`revoke` не имеет дополнительных полей. `purged` дополнительно содержит **ровно** `revokeSha256` (lowercase64hex), `sourceEmptyVerifiedAt`, `localMailClearedAt`, `metadataPurgedAt`. Оба первых proof timestamp >= revokedAt и <= metadataPurgedAt. `metadataPurgedAt` — durable время успешной DB-транзакции scrub, не время отправки ledger. Это заявление доверенного worker о проверках, не криптографическое доказательство отсутствия объектов/PII. Не хранить object keys/version IDs, email, bytes, названия, status capability или session hashes. Account/tenant UUID являются псевдонимными идентификаторами и требуют операторского retention ledger.

Canonical bytes: рекурсивная лексикографическая сортировка object keys по ASCII, затем `JSON.stringify` без отступов/перевода строки, UTF-8 без BOM; arrays отсутствуют. SHA-256 вычисляется над этими bytes, hash не включается в сам record. Strict parser ограничен8192 bytes, использует fatal UTF-8 decode, strict schema и требует byte-for-byte равенство повторно сериализованным canonical bytes (так отвергаются duplicate keys, whitespace и неканоническое JSON escaping). Pure API: `encodeErasureRecord(record) -> {record,key,bytes,sha256}`; `decodeErasureRecord(bytes, expectedKey, expectedLedgerId) -> record`; `validateErasurePair(revoke, purged?) -> {accountId,tenantId,requestId,state}`; `validateErasureLedger(records, expectedLedgerId) -> entries`, которая дедуплицирует идентичные записи, группирует request и проверяет уникальность account/tenant между группами. Entries сортируются по requestId; состояние — `revoked` или `purged`. Node crypto допустим; I/O, env и clock внутри модуля отсутствуют.

Запись adapter: PUT canonical bytes с `If-None-Match:*`, никогда overwrite/delete journal. При412 или неизвестном исходе PUT — прочитать существующий объект, сверить **полные bytes**, canonical parse/key/namespace; только идентичное содержимое означает idempotent success. Сохранить подтверждённый VersionId/hash в защищённом purge state; malformed/conflicting bytes — hard failure, не новая версия поверх. Terminal payload создаётся один раз после metadata commit, поэтому retry переживает потерянный ответ без нового timestamp.

Допустимая цепочка: отсутствует → revoke → purged; одинаковая запись любого шага повторяема. Pair validation требует равенства всех общих полей (кроме event), `purged.revokeSha256 == sha256(canonical revoke bytes)` и порядка timestamps выше. Purged без revoke, разные request для одного account/tenant либо разные account/tenant для одного request, namespace mismatch, неизвестная версия/event и conflicting duplicates останавливают restore. Revoke без purged — нормальное незавершённое удаление: restore закрывает доступ и очищает восстановленные данные. Наличие purged тоже требует очистить bytes старого snapshot, а не пропустить tenant. Идентичные повторные версии journal могут дедуплицироваться по bytes.

Restore adapter обязан перечислить весь настроенный ledger namespace с полной pagination до открытия приложения, проверять ожидаемый ledgerId backup и все пары, затем повторять suppression для каждого account/tenant. Pure module не доказывает полноту/свежесть listing: hash chain из двух записей не обнаруживает удаление целого request. Отдельные неизменяемость/retention journal, отсутствие delete markers, согласованный restore barrier без конкурентных writers и подтверждение выгрузки pending ledger receipts остаются обязательными условиями оператора/интеграционных тестов; при невозможности проверить их restore остаётся закрыт. Само наступление backup deadline никогда не создаёт purged record.

Приёмка pure-module: фиксированный canonical bytes/hash vector; exact round-trip; invalid UTF-8/duplicate keys/unknown fields/oversize/noncanonical UUID/date/key; mismatch каждого общего поля/hash; revoke-only, valid pair, late purge; orphan purged и conflicting request identities. Adapter PUT/412, permissions и полнота restore проверяются отдельно; эти pure tests не означают внешнюю durability.

## UI, файлы и приёмка

Account settings показывает «Скачать выбранную версию» и отдельное «Удалить аккаунт», точные последствия/сроки и явное подтверждение, без автоматического удаления при открытии страницы. Во время POST кнопки защищены от дубля; после202 owner UI очищается, открывается receipt status. 401 после потерянного ответа ведёт к receipt recovery, а не сообщает ложную отмену. Нет «Восстановить» для queued deletion; Trash restore остаётся иной функцией. Не выводить completed по elapsed timer.

Scope: новая migration/shared catalog/restore schema sync; account-deletion service/routes и узкие active-tenant gates в существующих services/auth; account purge module, maintenance hook, minimal receipt/ledger adapter; tests. UI — после backend shapes. Existing code/docs этим архитектурным пакетом не меняются. Acceptance на двух synthetic tenants: immediate old session/agent/share/grant/export denial; stale Actor и worker-after-CPU не создают bytes/rows; exact retry/response loss; конкурентный finalize либо committed до deletion и затем удалён, либо отказ; multiple versions/delete markers/orphans очищены, сосед/canary сохранены; partial S3 fail/abort не даёт purged, retry завершает; DB FK order/PII scrub и local mail; старый email challenge не воскрешает old tenant; ledger suppresses deletion в более старом restore snapshot; policy/deadline UI правдивы. Только после этих tests разрешён отдельный synthetic purge run. Working account deletion/real resources требуют явного назначения, не выполняются ради smoke.

## Следующий пакет после revoke slice и runtime grants

21.09.2026, ревью исполнения. Первый revoke slice прошёл изолированную приёмку; локальная schema16 работает с выключенным удалением. Следующая реализация должна завершить связку purge → внешний ledger → restore, а не оставлять статус pending бессрочно.

1. Отдельная защищённая запись purge job хранит ledger acknowledgement, phase, retry и результат. App-role UPDATE account_deletions не является разрешением terminal erasure. Worker получает отдельные точные права.
2. Использовать существующий maintenance: один tenant, до100 версий за проход, session/lock4388002, deadline/AbortSignal; повторный tenant→account marker check. Превышение policy deadline не означает успех.
3. Очищать весь точный tenant prefix: originals/bundles/derivatives/orphan versions/delete markers, только по VersionId. После batch читать оставшиеся версии с начала. Metadata остаётся до подтверждённого пустого listing; сосед и canary сохраняются.
4. Terminal metadata erasure — одна транзакция через узкую защищённую функцию с проверкой job/tenant/marker/blob phase. Она разрешает удаление withdrawn publications и FK-зависимостей только в этом пути; обычный DELETE по-прежнему запрещён. Сохранить минимальный обезличенный receipt/tombstones; квоты обнулить только этому tenant.
5. До anonymization согласовать email advisory lock с auth, удалить challenges/local mail; занятые challenges ведут к retry. Старый challenge не должен создать новый аккаунт после освобождения email. Удалить email/display name/password hash/старое имя.
6. Внешний ledger — отдельный versioned journal bucket вне отката DB/content backup. Append-only request/tenant/account UUID без PII; conditional PUT, точная сверка bytes при retry. Revoke record подтверждается до destructive purge, terminal record — после metadata commit; только затем durable purged.
7. Restore применяет актуальный ledger до открытия сервиса. Старый snapshot повторно подавляет deleting tenants и очищает восстановленные bytes/metadata. Недоступный/непроверенный ledger блокирует открытие. Snapshot-before-deletion → purge → restore проверяется синтетически с сохранным соседом; backup retention этим не доказывается.
8. Приёмка на isolated fixture: multi-version/delete markers/orphans, withdrawn publication/ready derivative, partial DELETE/abort, потерянный commit/ledger response, retry, permission denials/email race. UI подключает после backend acceptance; production enable требует подтверждённого retention и восстановления journal.

Это план реализации, не выполненные операции. Новые migration/job/ledger ещё не реализованы. Облачный journal bucket не создаётся без согласованной инфраструктуры и расходов.

### Исполнение и границы модулей

Обычный GC и account purge выполняются последовательными отдельными guarded invocations. Каждый использует ровно один dedicated DB client для lock4388002 и своих SQL/транзакций. Purge требует MAINTENANCE_DATABASE_URL отдельной worker роли; её права ограничены точными функциями и необходимым чтением. Existing GC сохраняет прежние credentials/DML. Guard одного соединения не разрешает SQL другого; общий advisory lock предотвращает пересечение invocation. Вариант расширения worker правами всего GC отменён.

Canonical record validation остаётся в packages/erasure-ledger.ts, injected append/read в scripts/erasure-ledger-adapter.ts. Отдельный S3 transport читает точные VersionId, полностью обходит версионный listing и отклоняет delete markers; он не должен незаметно читать latest вместо указанной версии. Credentials/config принадлежат worker, а не codec/adapter. Эти границы не являются доказательством готовности реального journal bucket.


## Интеграция журнала при восстановлении

`loadBackup()` сверяет ledgerId envelope с настроенным namespace и полностью читает/проверяет внешний журнал до восстановления. Ошибка не разрешает startup. Журнал не откатывается вместе с DB/content.

Порядок: `restoreDatabase()` → `restoreObjects()` → `remapAndClose()` → `applyErasureLedgerToRestoredTarget()` → `verify()`. Последний шаг впервые создаёт приложение, поэтому suppression должна завершиться раньше него.

Reconciliation при restore — отдельная процедура: старый snapshot может не содержать receipt/job, а snapshot с job.phase=purged всё равно может только что восстановить bytes. Для каждого затронутого tenant повторно подавляются доступы, удаляются точные восстановленные версии и очищаются metadata/mail. Повторный запуск безопасен. Restore не пишет в journal и не заменяет исторические bytes/hashes/timestamps новыми датами проверки.

Приёмка: tenant присутствует до snapshot, удаляется после snapshot, затем восстанавливается старая копия. Его bytes/PII отсутствуют, прежние login/share/grants не работают; сосед сохраняет exact-export/new-share. Отдельно проверяются revoke-only журнал, повтор reconciliation, malformed/unavailable журнал (app не создаётся), неизменность journal bytes/versions. Это не подтверждает production backup retention.
