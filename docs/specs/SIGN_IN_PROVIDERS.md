# Вход через Яндекс ID, VK ID и SSO компании; ограничения входа по почте; заметки владельца

**Статус:** принято к реализации 24.09.2026. § 1 «Уже есть полка?» и § 8–10 (временные полки, объединение, ссылка для входа от агента) — 24.09.2026.

**Зачем.**
- **Авторизация.** С 01.12.2023 владелец сайта — гражданин РФ обязан авторизовать пользователей из России одним из способов ч. 10 ст. 8 149-ФЗ: телефон, ЕСИА, ЕБС или информационная система российского владельца. С 07.07.2026 за нарушение штрафуют по ст. 13.55 КоАП. Вход по коду на иностранный почтовый ящик (Gmail) юридические СМИ приводят как нарушение.
- **Комментарии.** Тексты получателей, которые читают другие пользователи, по буквальному чтению ст. 10.1 делают Полку организатором распространения информации (ОРИ).

**Решения владельца:**
1. Добавить вход через Яндекс ID и VK ID. Новые регистрации по коду на почту — только на российских почтовых доменах. Существующие аккаунты продолжают входить.
2. На polochka.app заменить комментарии получателей заметками владельца.
3. Дать компаниям подключать единый вход, чтобы сразу получала доступ вся компания.

## 1. Внешние поставщики входа

### Общая схема

Полка — **клиент** OAuth 2.0 / OpenID Connect. С собственным OAuth-сервером Полки для агентов (`/oauth/*`, `oauth.ts`) эта часть не связана: у них разные таблицы, cookie и маршруты.

Поток — authorization code на сервере:
- `GET /api/auth/idp/:provider/start?next=/путь` — начало входа;
- `POST /api/auth/idp/:provider/link` — привязка к уже вошедшему аккаунту: нужна сессия и проверка Origin;
- Полка отвечает 303 на страницу авторизации поставщика;
- поставщик возвращает пользователя на `GET /api/auth/idp/:provider/callback`;
- Полка обменивает код на токен на сервере, читает профиль, выдаёт свою сессию (`polka_session`, как при входе по коду) и отвечает 303 на `next`.

**Защита:**
- **state** — 32 случайных байта. Сравнивается с тем, что лежит в cookie браузера, за постоянное время.
- **PKCE S256** — `code_verifier` из 32 случайных байт, всегда.
- **nonce** — для OIDC, проверяется в `id_token`. У Яндекс ID и VK ID `id_token` с nonce в веб-потоке нет, поэтому там защита — state и PKCE.
- **Состояние потока** хранится в cookie `polka_idp`, а не в базе:
  - шифрование AES-256-GCM, ключ выводится из `LINK_KEY` (HMAC с меткой назначения);
  - флаги HttpOnly, `SameSite=Lax` (иначе браузер не отдаст её на возврате с чужого сайта), `Path=/api/auth/idp`, 10 минут;
  - в cookie: поставщик, state, verifier, nonce, `next`, аккаунт для привязки и срок;
  - на возврате cookie стирается, повтор того же ответа отклоняется.
- **Строгий redirect URI** — `APP_ORIGIN + /api/auth/idp/<provider>/callback`. Он не собирается из запроса, у поставщика регистрируется точно такой же.
- **Где могут появиться секреты:**
  - токены поставщика и `client_secret` не попадают ни в URL, ни в журналы, ни в базу: access token живёт только в памяти запроса;
  - код авторизации приходит в query, так устроен OAuth. Он одноразовый, живёт минуты и без verifier бесполезен;
  - Полка отвечает 303, поэтому URL с кодом не остаётся в истории браузера. `Referrer-Policy: no-referrer` уже стоит на всех ответах.
- **Запросы к поставщику:**
  - только `https:` (`http:` допускается лишь для loopback в тестах);
  - таймаут 10 с, ответ не больше 256 КБ;
  - ошибки поставщика пользователю не пересказываются: только код причины на странице входа (`/signup?idp_error=…`).
- **Куда можно вернуться.** `next` проверяется так же, как `safeNext` в интерфейсе: только путь этой же установки.

### Яндекс ID

- Авторизация: `https://oauth.yandex.ru/authorize`. Параметры: `response_type=code`, `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method=S256`, `scope=login:email login:info`.
- Токен: `POST https://oauth.yandex.ru/token`. Параметры: `grant_type=authorization_code`, `code`, `code_verifier`, `client_id` и `client_secret` в Basic-заголовке.
- Профиль: `GET https://login.yandex.ru/info?format=json`, заголовок `Authorization: OAuth <token>`.
  - `id` — subject;
  - `default_email` — почта;
  - `real_name` или `display_name` — имя.
- Подтверждена ли почта, Яндекс явно не сообщает. Но адрес по умолчанию всегда подтверждён:
  - это собственный ящик Яндекса;
  - или ящик организации Яндекс 360 на домене, который организация подтвердила в DNS;
  - или адрес, с которым зарегистрировались «с любой почтой», — такой адрес подтверждают кодом.

  Поэтому по умолчанию `YANDEX_EMAIL_VERIFIED=true`. Оператор может выключить: тогда почта из Яндекса не связывает аккаунты и не даёт доступ по домену.
- Настройки: `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`. Без обеих вход выключен.

### VK ID

VK ID работает по OAuth 2.1 с обязательным PKCE. Актуальная документация VK ID (2026) указывает адреса на домене `id.vk.ru` (раньше — `id.vk.com`). Полка использует `id.vk.ru`; адреса можно переопределить для тестов.

- Авторизация: `https://id.vk.ru/authorize`. Параметры: `response_type=code`, `client_id`, `redirect_uri`, `state` (не короче 32 символов), `code_challenge`, `code_challenge_method=S256`, `scope=email`.
- Возврат: `code`, `state`, `device_id`.
- Токен: `POST https://id.vk.ru/oauth2/auth`, форма. Параметры: `grant_type=authorization_code`, `code`, `code_verifier`, `client_id`, `device_id`, `redirect_uri`, `state`. Ответ: `access_token`, `user_id`, `id_token` и др.
  - `client_secret` в потоке VK ID не передаётся: код защищён PKCE.
  - `state` в ответе должен совпасть с отправленным.
- Профиль: `POST https://id.vk.ru/oauth2/user_info`, форма `client_id`, `access_token`. Из `user` берутся `user_id` (subject), `email`, `first_name` и `last_name`.
- Признака подтверждения почты у VK ID нет (поле `verified` означает верифицированную страницу, а не почту). Поэтому по умолчанию `VK_EMAIL_VERIFIED=false`: почта из VK сохраняется в привязке, но не связывает аккаунты и не даёт доступ по домену. **Проверить** у VK, подтверждается ли почта аккаунта; если да — включить.
- Настройки: `VK_CLIENT_ID`. Вход выключен, пока он не задан.

### Свой OIDC (Keycloak, Avanpost, ADFS и др.) для своей установки

- **Настройки:**
  - `OIDC_DISCOVERY_URL` — адрес `…/.well-known/openid-configuration`;
  - `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`;
  - `OIDC_SCOPES` — по умолчанию `openid email profile`;
  - `OIDC_NAME` — подпись кнопки, по умолчанию «Единый вход компании».
- **Необязательно:**
  - `OIDC_ALLOWED_DOMAINS` — войти можно только с почтой этих доменов;
  - `OIDC_ORG_CLAIM` и `OIDC_ORG_VALUE` — вход только при `claim = value`. Если claim — массив (например, `groups`), значение должно в нём быть.
- **Discovery.** Документ читается при первом входе и кешируется на час. `issuer` в нём должен совпадать с префиксом адреса discovery.
- **Проверка `id_token`:**
  - подпись RS256, PS256 или ES256 по ключу из `jwks_uri` с тем же `kid`;
  - `iss`, `aud` (содержит `client_id`), `azp`, если `aud` несколько, `exp` и `iat` с допуском 2 минуты, `nonce`;
  - subject — `sub`, почта — `email`, подтверждена, только если `email_verified === true`.
- **Клиент:** confidential, `client_secret_basic`.

**Как компания подключает свой IdP.**
1. В IdP создать клиента OpenID Connect:
   - тип confidential, authorization code, PKCE S256;
   - redirect URI `https://<ваша Полка>/api/auth/idp/oidc/callback`;
   - scopes `openid email profile`;
   - в `id_token` передавать `email` и `email_verified`.
2. В `.env` установки задать `OIDC_*`, при желании — `OIDC_ORG_LIBRARY` (раздел 2).
3. Перезапустить. Кнопка с `OIDC_NAME` появится на странице входа.

### Яндекс 360 для бизнеса и VK WorkSpace

- **Яндекс 360 для бизнеса** в SSO — *поставщик услуг* (SAML 2.0): сотрудники входят в Яндекс 360 через IdP компании (Active Directory, Keycloak, Avanpost). Сторонним приложениям Яндекс 360 свой SAML или OIDC не отдаёт.

  Поэтому организация на Яндекс 360 входит в Полку **через Яндекс ID**:
  - аккаунт сотрудника — аккаунт организации с адресом `ivan@company.ru`;
  - если у компании настроен SSO в Яндекс 360, сотрудник по пути ещё раз проходит её IdP;
  - доступ всей компании даёт `ORG_DOMAINS=company.ru=…` (раздел 2).
- **VK WorkSpace / VK Teams.** Для входа в сторонние сервисы предусмотрен VK ID. Если у компании своя установка VK WorkSpace с OIDC-провайдером, её подключают как «свой OIDC». **Проверить** на конкретной установке.

### Аккаунты и привязки

Миграция `032_account_identities.sql` создаёт таблицу `account_identities`:
- `account_id` → accounts, `ON DELETE CASCADE`;
- `provider` (`yandex` | `vk` | `oidc`), `subject`;
- `email` — почта, которую поставщик сообщил при привязке, или NULL;
- `email_verified`;
- `created_at`, `last_used_at`;
- `UNIQUE(provider, subject)`.

Номер 031 занят параллельной веткой (`031_content_filter.sql`). Рецепты прав и проверки каталога принимают набор 1…32 с 031 или без него, так что ветки сливаются в любом порядке. После слияния обеих проверку можно сделать строгой.

**Что происходит при входе через поставщика:**
1. Привязка `(provider, subject)` уже есть → вход в её аккаунт, если он не заблокирован и не удаляется.
2. Идёт привязка из настроек (`link`) → привязка к вошедшему аккаунту. Если этот `subject` уже привязан к другой полке — отказ.
3. Поставщик **подтвердил** почту, и есть аккаунт с этой почтой → привязка к нему (так пользователь по коду на `ivan@yandex.ru` получает вход через Яндекс ID без второй полки).
4. Иначе — новый аккаунт:
   - `email` = подтверждённая почта, если она ни у кого не занята, иначе NULL;
   - `email_verified_at` ставится, только если почта подтверждена;
   - неподтверждённая почта аккаунту не присваивается;
   - действуют те же суточные лимиты новых полок (`EMAIL_SIGNUP_DAILY_LIMIT`, `EMAIL_SIGNUP_DAILY_PER_IP`);
   - в режиме `EMAIL_SIGNUP=invite` новая полка открывается только для приглашённой подтверждённой почты.

   Ограничение доменов (раздел 3) на поставщиков не действует: авторизацию проводит российская система.

### «Похоже, у вас уже есть полка»

Реальный случай: у владельца был аккаунт `artem`, созданный оператором (почта на gmail). Он нажал «Войти с Яндекс ID», а почта в Яндексе на yandex.ru — и молча получил вторую, пустую полку. Поэтому новая полка не создаётся молча в браузере, где уже входили.

**Подсказка без слежки.** После входа браузер запоминает в своём `localStorage` (с `try/catch`) только `{displayName, method, at}`: отображаемое имя полки, способ входа и время. Ни идентификаторов, ни почты. Временная полка (§ 8) подсказку не оставляет. На сервер уходит только флаг `known=1`, без содержимого подсказки.

**Вход через поставщика.**
- Кнопки поставщиков в браузере с подсказкой добавляют `known=1` к `/api/auth/idp/:provider/start`; флаг едет в зашифрованной cookie потока.
- На возврате, если вход **открыл бы новую полку** (нет привязки `(provider, subject)` и нет полки с подтверждённой почтой), Полка ничего не создаёт:
  - профиль поставщика кладёт в память процесса на 10 минут (`sign-in-pending.ts`, не больше 5000 записей);
  - браузеру ставит cookie `polka_idp_pending` (HttpOnly, Lax, `Path=/api/auth/idp`, 10 минут) — зашифрованное AES-256-GCM имя записи;
  - отвечает 303 на `/signup/choose?next=…`. В URL нет ни почты, ни subject, ни имени.
- `/signup/choose`: «Похоже, у вас уже есть полка «<имя из подсказки>». Войдите в неё — и мы привяжем Яндекс ID к ней».
  - «Войти в существующую полку» → обычный вход (код, логин, другой поставщик) с меткой `link=pending` и `next=/signup/linked?next=…`. Страница `/signup/linked` вызывает `POST /api/auth/idp/pending/link`: привязка по обычным правилам (подтверждённая почта, уникальность `(provider, subject)`; уже привязанный к другой полке — отказ `linked`).
  - «Создать новую полку» → `POST /api/auth/idp/pending/create`: то же, что сделал бы возврат (лимиты регистраций, режим приглашений).
  - `GET /api/auth/idp/pending` сообщает странице только поставщика. Запись одноразовая; через 10 минут, после перезапуска или в другом браузере — 410.
- Без подсказки всё как раньше. После первой регистрации в этом браузере один раз видна строка «Уже есть полка? Привяжите этот вход к ней в «Способах входа»».

**Код на почту.** Браузер с подсказкой отправляет `knownShelf: true` в `/api/auth/email/verify`. Если код верный, а полки на адресе нет, сервер отвечает 409 `{reason: "new_shelf"}`, не тратя код. Страница задаёт тот же вопрос. «Создать новую полку» повторяет запрос с `createNew: true`, «Войти в существующую» возвращает к выбору способа входа. Существовала ли полка, сервер сообщает только тому, кто ввёл верный код; форма запроса кода по-прежнему отвечает одинаково.

**Отвязка.** «Способы входа» в настройках (`/settings/agents`): можно отвязать поставщика, если у аккаунта остаётся другой способ входа — почта или другая привязка.

**Удаление аккаунта.** Триггер миграции 032 удаляет привязки, как только у аккаунта появляется `deletion_requested_at`. Это происходит при подтверждении удаления, при восстановлении из копии (`register_restored_erasure`) и при окончательной очистке. Функцию `terminal_erase_account_metadata` 032 не переопределяет, поэтому с 031 и последующими миграциями не конфликтует.

## 2. Доступ компании

Настройки установки (оператора). Самостоятельная настройка домена администратором библиотеки отложена: без проверки владения доменом администратор чужой библиотеки мог бы собрать к себе сотрудников `sberbank.ru` и увидеть их почту.

- **`ORG_DOMAINS=company.ru=<uuid библиотеки>[:reader|curator], …`.**
  - Кто входит через поставщика с **подтверждённой** почтой этого домена (не поддоменов), становится участником библиотеки шаблонов с указанной ролью (по умолчанию reader).
  - Роль admin по домену не выдаётся.
  - Публичные почтовые домены (yandex.ru, mail.ru, gmail.com и т. п.) в `ORG_DOMAINS` запрещены: установка не запустится.
- **`OIDC_ORG_LIBRARY=<uuid>[:reader|curator]`.** Каждый, кто вошёл через «свой OIDC», становится участником этой библиотеки. IdP компании сам решает, кого пускать; дополнительно действуют `OIDC_ALLOWED_DOMAINS` и `OIDC_ORG_CLAIM`.

**Правила автоматического вступления:**
- Библиотека должна быть активной.
- Если участник уже есть или был исключён (строка membership существует в любом состоянии), ничего не меняется. Исключённого администратором домен обратно не добавит.
- Вступление пишется в журнал библиотеки (`template_library.domain_joined`) и в audit.
- Вход по коду на почту в библиотеку не добавляет. Сотрудник, который раньше входил по коду, добавится при первом входе через поставщика.

## 3. Вход по коду на почту

- **`EMAIL_SIGNUP_DOMAINS=any|ru-only|<список>`** — на каких доменах можно **открыть новую полку** по коду:
  - `any` — по умолчанию для своих установок, как раньше;
  - `ru-only` — по умолчанию в `deploy/hosted`. Встроенный список:
    - Яндекс: yandex.ru, ya.ru, yandex.com, yandex.by, yandex.kz, yandex.ua, narod.ru;
    - Mail.ru Group / VK: mail.ru, bk.ru, list.ru, inbox.ru, internet.ru, vk.com, vk.ru;
    - Рамблер: rambler.ru, ro.ru, lenta.ru, autorambler.ru, myrambler.ru, rambler.ua;
    - домен самой установки (хост `APP_ORIGIN`) и его родительский домен;
  - список — домены через запятую, `ru-only` можно указать элементом списка.
- **Существующие аккаунты** на любом домене по умолчанию входят по коду, как раньше: правовые пересказы спорят, распространяется ли требование на ранее зарегистрированных, а резкое отключение запирает людей.
  - **`EMAIL_LOGIN_DOMAINS=any|signup`.** `signup` отключает коды и для существующих аккаунтов вне разрешённых доменов. Перед этим попросите их привязать Яндекс ID или VK ID в «Способах входа».
- **Как выглядит отказ.**
  - Сервер отвечает на запрос кода одинаково, есть аккаунт или нет, и письмо на неразрешённый домен без аккаунта просто не уходит. Иначе по форме можно было бы узнать, у каких gmail-адресов есть полка.
  - Интерфейс знает список доменов из `/api/capabilities` (`emailSignupDomains`). При вводе адреса вне списка он заранее пишет: «Новые полки по почте открываются на адресах Яндекса, Mail.ru, Рамблера и VK. Если на этом адресе полки ещё нет, войдите через Яндекс ID или VK ID» и показывает эти кнопки.
- `EMAIL_SIGNUP=invite` и `EMAIL_SIGNUP_ALLOW` действуют как раньше. Адрес из `EMAIL_SIGNUP_ALLOW` открывает полку и вне списка доменов: это приглашение оператора.

## 4. Комментарии: `COMMENTS_MODE=on|owner-notes|off`

- **`on`** — по умолчанию для своих установок, как описано в [COMMENTS.md](COMMENTS.md).
- **`owner-notes`** — по умолчанию в `deploy/hosted`.
  - **Кто пишет.** Только владелец работы — на странице работы или по своей ссылке — и его агент: `polka_note`, `polka_comments`, `polka_resolve_comment`.
  - **Где живёт заметка.** Она привязана к ссылке, как ветка комментариев: получатели этой ссылки видят заметки только для чтения, без полей ввода.
  - **Реакции** выключены: не ставятся и не показываются.
  - **Писем** о заметках нет никому, кроме писем оператору о подозрительном тексте.
  - **Старые комментарии получателей и реакции** скрыты от всех, включая владельца и агентов, но не удалены. Если вернуть `on`, они снова видны.
  - **Запись получателя** (комментарий, ответ, реакция, удаление, «решено») отклоняется с 403: «На этой Полке получатели не оставляют комментарии. Напишите автору напрямую».
- **`off`** — обсуждений нет:
  - маршруты получателя отвечают 404;
  - оверлей во фрейм не добавляется;
  - владелец и агент получают пустой список с `mode: "off"`, запись отклоняется.

**Где видно режим:**
- `/api/capabilities` (`commentsMode`);
- ответы обсуждений (`mode`);
- `/llms.txt`, `SKILL.md`, описание MCP-инструментов и [connect-agents.md](../connect-agents.md).

**Интерфейс:**
- у получателя в `owner-notes` нет «Комментировать» и реакций на выделении, в ленте заголовок «Заметки автора»;
- у владельца — «Заметки».

Правовое основание — вариант «Г» из разбора рисков: заметки — контент владельца, а не обмен сообщениями между пользователями.

## 5. Интерфейс входа

- **Кнопки.** На `/signup` и на странице входа (`/?login=1`) кнопки «Войти с Яндекс ID», «Войти с VK ID» и, если настроен, «<OIDC_NAME>». Показываются, только если поставщик включён (`signInProviders` в `/api/capabilities`).
- **Текст кнопок** — официальный текст поставщиков: «Войти с …». Яндекс запрещает менять текст, цвет и иконку своей кнопки.
- **Цвета:**
  - Яндекс ID — чёрная кнопка с красным знаком «Я»;
  - VK ID — синяя `#0077FF` с белым знаком.
  - Иконки упрощённые, в SVG. Перед публикацией их стоит заменить официальными SVG из разделов «Оформление» у Яндекса и VK.
- **Возврат.** `next` передаётся поставщику через cookie потока и возвращается после входа. Поэтому подключение агента (`/oauth/consent?request=…`) продолжается после входа через поставщика так же, как после кода. Cookie запроса подключения (`/oauth`, Lax, 10 минут) переживает поход к поставщику.
- **Ошибки** показываются на `/signup` по коду `idp_error`:
  - `state` — запрос устарел или открыт в другом браузере;
  - `denied` — вы отменили вход;
  - `provider` — поставщик не ответил;
  - `blocked` — аккаунт заблокирован или удаляется;
  - `signup` — регистрация закрыта или по приглашению;
  - `domain` — почта не из разрешённого домена компании;
  - `linked` — этот аккаунт поставщика уже привязан к другой полке.
- **Журнал.** Каждый неудачный возврат от поставщика пишет строку `{"event":"idp.callback_failed","provider":…,"code":…}`: код из списка выше, `rate_limited` или `internal`. Ни токенов, ни почты, ни строки запроса.
- **`/login`** — псевдоним: 303 на `/signup`, безопасный `next` (путь этой установки) сохраняется.
- **Страница согласия агента** (`/oauth/consent`) показывает, куда пойдут работы: «Работы будут сохраняться в полку «<имя>» (почта …, Яндекс ID, логин …)» и «Это не та полка? Выйти и войти в другую» (выход и возврат на вход с тем же запросом). Способы берутся из `GET /oauth/authorize/details` (`account`). Так коннектор (Claude.ai, ChatGPT, Codex, Claude Code) попадает в нужную полку, а не в тестовую, где браузер случайно был авторизован.
- **Без сессии** та же страница не уводит на вход, а спрашивает: «Начать без регистрации» (§ 8) или «Войти». Если браузер помнит полку, первой кнопкой идёт «Войти в полку «<имя>»».
- **«Открой мою Полку».** На `/signup`, после подключения на странице согласия, на странице «Агенты» и в плашке временной полки есть строка: подключённого агента можно попросить ссылку для входа (§ 10). Фразу можно скопировать.

## 6. Персональные данные

В политику ([privacy.md](../legal/privacy.md)) добавляется новая строка:
- **Что хранится:** идентификатор пользователя у поставщика, почта и имя, которые он передал при входе.
- **Основание:** исполнение соглашения (п. 5 ч. 1 ст. 6 152-ФЗ) — вход в аккаунт.
- **Сколько хранится:** пока существует привязка или аккаунт.

Токены поставщика не сохраняются. Передача данных поставщику: Полка сообщает ему только, что пользователь входит в Полку (client_id и адрес возврата).

## 7. Проверки

- **Потоки с поддельными поставщиками** (локальный HTTP-сервер):
  - успешный вход и повторный вход;
  - несовпадение `state`;
  - отсутствующая или чужая cookie;
  - неверный `code_verifier` (поставщик отвечает ошибкой);
  - `nonce` и подпись `id_token` в OIDC;
  - неподтверждённая почта не связывает аккаунты;
  - подтверждённая почта связывает;
  - блокированный аккаунт;
  - привязка из настроек, повторная привязка к другой полке;
  - автоматическое вступление по домену с учётом исключённых.
- **Политика доменов:** новая полка вне списка не создаётся, существующая входит, `EMAIL_LOGIN_DOMAINS=signup`.
- **Режимы комментариев:** `on`, `owner-notes` (запись получателя, скрытие старых, реакции, письма, `polka_note`), `off`.
- **Миграция и права:** каталог, рецепты прав, привязки стираются при удалении аккаунта.
- **Одна полка** (`tests/one-shelf.test.ts`):
  - подсказка → вопрос → вход в существующую → привязка; повторный вход поставщиком открывает ту же полку;
  - «Создать новую» создаёт; без подсказки вопроса нет;
  - в URL нет данных поставщика; запись истекает, чужая и поддельная cookie не подходят;
  - код на новый адрес с подсказкой — 409 `new_shelf`, код остаётся годным;
  - страница согласия показывает полку и способы входа;
  - временная полка: только с настоящим запросом подключения и Origin; второй агент — в ту же полку; ссылки нет, есть `claimUrl` (агенту и в интерфейсе); закрепление Яндекс ID и почтой привязывает к этой же полке; столкновение → «Объединить» (агент продолжает работать в основной полке); пароль из временной полки с работами спрашивает, «Отмена» ничего не меняет; обслуживание удаляет простаивающую (через конвейер удаления и напрямую вместе с объектами);
  - «Открой мою Полку»:
    - закреплённая полка получает подсказку без секрета;
    - грант без `sign_in` токена не получает; у существующих подключений переключатель выключен;
    - ссылка временной полки: просмотр страницы ничего не тратит, вход в уже вошедшем браузере без выбора отклоняется;
    - токен только во фрагменте и только хешем, работает один раз, истекает, проверяется Origin;
    - слабая сессия не может привязать способ входа, управлять агентами и удалять; код на почту из неё не закрепляет полку;
    - настоящий вход из слабой сессии предлагает перенести работы и не привязывает identity к временной полке;
    - статический токен и выключенный переключатель отклоняются, действует лимит в час, в журнале нет токена; `polka_open_shelf` есть только у OAuth-подключений;
  - при объединении неотмеченные агенты отключаются; закреплённую тем временем полку «Объединить» не трогает.
- **Объединение** (`tests/account-merge.test.ts`): пробный прогон печатает числа и ничего не меняет; без `--proof` ничего не происходит; настоящий переносит всё, старые ссылки открываются, токен и ключ продления работают и сохраняют в основную полку, объекты лежат под префиксом основной, источник удалён (почта и имя стёрты), журнал `account.merged` с номером обращения; отказ при блокировке, отключённом аккаунте и одном и том же аккаунте.

## 8. Временные полки (без регистрации)

**Зачем.** Подключить агента можно сразу, без регистрации, — и при этом один браузер всегда попадает в одну полку.

**Как открывается.**
- На странице согласия без сессии: «Начать без регистрации» → `POST /oauth/authorize/provisional {request}`.
- Защита от ботов:
  - запрос из браузера со страницы Полки (общая проверка Origin);
  - только при живом запросе подключения этого браузера (`request` и cookie `polka_oauth` должны совпасть);
  - одна полка на один запрос подключения, 5 в час с IP и общие суточные лимиты регистраций (установка, сеть, подсеть).
- Создаётся аккаунт `guest-<id>` без почты, с именем «Временная полка» и `accounts.provisional_at` (миграция 036), и его тенант с квотой 20 МБ (после закрепления — обычная).
- Браузер получает обычную сессию (HttpOnly, Strict) на 30 дней. Каждое посещение (`/api/session`) продлевает её на 30 дней, не чаще раза в сутки.
- Аналитика: `signup_completed {method: "provisional"}`.
- Второй агент в том же браузере видит «Работы пойдут в вашу полку (временная, этот браузер)», и новая полка не создаётся.

**Что можно.** Сохранять приватно, смотреть, работать с агентами.

**Что нельзя** до закрепления (ч. 10 ст. 8 149-ФЗ: авторизация через российские системы). Всё, что делает написанное видимым другим, проходит одну проверку `assertAuthorisedForPublic` (`provisional.ts`):
- ссылки — единая точка `enableShareInTransaction`: веб, `polka_share`, `polka_publish`, HTTP API;
- публикация в библиотеку шаблонов, создание библиотеки и приглашения;
- комментарии и реакции на чужих ссылках.

Отказ — 403 с текстом «Полка ещё не закреплена: чтобы выдать ссылку, владелец должен войти через <способы этой установки>: <origin>/claim» (способы берутся из настроек: Яндекс ID, VK ID, почта) и полем `claimUrl`. `polka_publish` и `POST /api/v1/publish` при этом сохраняют работу: `state: "saved"`, `url: null`, `linkUnavailableReason`, `claimUrl`. В интерфейсе вместо кнопки ссылки — «Закрепить, чтобы поделиться».

**Плашка в приложении:** «Полка живёт только в этом браузере. Закрепите её — войдите с Яндекс ID или по почте». Ниже — срок удаления и «Потеряли вход? Попросите агента: «Открой мою Полку»». В окне выхода — предупреждение о том же.

**Закрепление** (`/claim`) привязывает способ входа **к этой же полке** и ставит `accounts.claimed_at`. Новая полка не создаётся. Закреплять может только сессия, открытая в этом браузере кнопкой «Начать без регистрации». Сессия, открытая ссылкой от агента (§ 10), слабая. Из неё /claim предлагает войти через Яндекс ID, VK ID или по почте в свою полку — существующую или новую — и потом перенести работы, но способ входа к временной полке **не привязывает**. Для поставщика флаг `carry` едет в cookie потока, для почты и пароля — то же столкновение.
- Яндекс ID или VK ID — обычная привязка (`POST /api/auth/idp/:provider/link`). Подтверждённая почта поставщика становится почтой полки, если она свободна.
- Почта — код на адрес разрешённого домена (`EMAIL_SIGNUP_DOMAINS`). `/api/auth/email/verify` с сессией временной полки и адресом без полки привязывает адрес.
- Аналитика: `shelf_claimed {method}`.

**Столкновение.** Способ входа уже открывает другую полку: привязанный `(provider, subject)`, подтверждённая почта поставщика, код на существующий адрес или логин и пароль из браузера с временной полкой, где есть работы или живые подключения. Тогда Полка:
- ничего не привязывает и не выдаёт сессию;
- кладёт запись в память на 10 минут: cookie `polka_claim`, `Path=/api/account/claim`;
- открывает `/claim`: «У вас уже есть полка «X». Объединить?»

Варианты:
- «Объединить» (`POST /api/account/claim/merge {connections}`) — объединение § 9 из временной в ту полку, журнал с actor `signup`, затем вход в ту полку. Поставщик привязывается к ней. Каждое подключение агента, которое переедет, показано отдельной строкой; по умолчанию не отмечено ни одно, неотмеченные отключаются. Слияние отказывает, если временную полку тем временем закрепили в другой вкладке. Из слабой сессии объединять можно только с полкой, в которую этот браузер только что вошёл по-настоящему;
- «Открыть ту полку без объединения» (`/switch`);
- «Отмена» (`/cancel`): выданная сессия той полки удаляется.

**Удаление.** Полку удаляет обслуживание, если за 30 дней не было ни одного из событий: посещения (живой сессии), обращения агента, сохранения.
- При `ACCOUNT_DELETION_ENABLED=true` — через обычный конвейер удаления (`account_deletions` → `account_purge_jobs`, как подтверждённое удаление).
- Иначе обслуживание само закрывает полку, удаляет все версии объектов под префиксом её тенанта и её строки. Аккаунт и тенант остаются пустыми отметками без личных данных. Полку со ссылками, заблокированным содержимым или участием в библиотеках оно только закрывает.

## 9. Объединение двух полок одного человека

`scripts/account-merge.ts --from <логин|почта|id> --into <логин|почта|id> --proof <номер обращения> [--dry-run] [--reason "…"] [--json]` (`npm run account:merge`) и «Объединить» из § 8 используют `apps/server/account-merge.ts`.

**Одна транзакция, та же дисциплина блокировок:**
- два тенанта, затем два аккаунта `FOR UPDATE` в порядке id;
- затем, как при удалении, подключения, загрузки, работы, ссылки и производные источника.

**Отказы:**
- один и тот же аккаунт;
- любой из двух отключён или удаляется;
- у источника заблокированное содержимое (незакрытый `moderation_blocks`, заблокированная ссылка, заблокированный комментарий);
- у источника публикации в «Ленте»;
- у источника идёт загрузка, URL-импорт или сборка.

**Что переносится:**
- **Объекты.** Удаление чистит хранилище по префиксу `<tenant>/`, поэтому каждая версия объекта источника копируется (CopyObject с версией) по тому же пути под префиксом получателя. Строки `revisions`, `revision_files`, `revision_derivatives`, `upload_files` и `uploads.object_version` указывают на копии. Оригиналы удаляются после фиксации; неудаленные скрипт перечисляет. При ошибке копии удаляются.
- **Работы, версии, файлы, производные, ссылки, обсуждения, жалобы, снятые блокировки** — одним SQL-выражением с CTE: внешние ключи включают тенант и проверяются в конце выражения. Готовые производные неизменяемы, поэтому их строки удаляются и вставляются заново с тем же id.
- **Папки:** одноимённые сливаются с папкой получателя.
- **Ссылки.** Токен ссылки выводится из её id, поэтому **старые ссылки открываются**.
- **Подключения агентов** вместе с операциями, импортами, запросами и ключами продления OAuth и журналом — вторым выражением. **Токены продолжают работать** и сохраняют в полку получателя.
- **Заметки и реакции** источника на чужих полках, `resolved_by`.
- **Привязки поставщиков**, если у получателя нет того же поставщика. Остальные остаются у источника и указываются в отчёте.
- **Участие в библиотеках.** У получателя появляется участие с наибольшей из двух ролей, участие источника отзывается, `template_libraries.created_by` переносится.
- **Почта источника** переезжает, только если у получателя её нет.
- **Статистика** перекладывается на ключ получателя через удаление и вставку (у runtime-роли нет UPDATE). `signup_completed` источника удаляется. Возражение любой из сторон побеждает.
- **Объём:** `used_bytes` суммируется. Превышение квоты указывается в отчёте.

**Доказательство.** Без `--proof` (номер обращения, по которому подтверждено, что обе полки принадлежат одному человеку) настоящее слияние оператора не выполняется. Номер пишется в журнал (`moderation_events.authority`).

**Источник** после слияния удаляется, а не просто отключается:
- при `ACCOUNT_DELETION_ENABLED=true` — через конвейер удаления;
- иначе закрывается как удалённый: `deletion_requested_at`, стёрты почта и имя, триггер стирает оставшиеся привязки.

В `moderation_events` пишется `account.merged` (actor `operator-script` или `signup`, детали — получатель и числа), в журнал получателя — `account.merged`. Строки приглашений и журнала библиотек, где упомянут источник, остаются как история; при окончательной очистке их обезличивает триггер удаления.

`--dry-run` печатает те же числа и ничего не меняет.

## 10. «Открой мою Полку»: вход по просьбе к агенту

«Как вернуться в полку, куда сохраняет мой Claude, если я вышел?» Попросить агента: «Открой мою Полку». Агент вызывает MCP-инструмент `polka_open_shelf` (у OAuth-подключений) или `POST /api/v1/sign-in-link` и отдаёт ссылку как есть, сам её не открывает.

**Закреплённая полка — подсказка без секрета.** Ответ: `{kind: "hint", url: "<origin>/signin?shelf=<hint>"}`.
- `hint` — зашифрованный (AES-256-GCM) указатель на полку на 30 дней. Он не даёт входа.
- `/signin` показывает имя полки и её способы входа: привязанных поставщиков, почту в виде `ar…@yandex.ru`, логин. Человек входит обычным способом.
- Агентский грант, даже широкий, никогда не превращается в сессию закреплённой полки.

**Незакреплённая временная полка — одноразовая ссылка.** Другого пути внутрь у неё нет. Ответ: `{kind: "link", url: "<origin>/enter#<token>"}`.
- **Условия выдачи:**
  - подключение через OAuth;
  - ему дано отдельное право `sign_in` («Давать ссылку для входа»). Право показано на странице согласия, по умолчанию выключено и не входит в `context`;
  - владелец не выключил переключатель на странице «Агенты» (`agent_connections.sign_in_links`).
- **Миграция 036:** у всех существующих подключений переключатель выключен. У новых он включается, только если на согласии отмечено `sign_in`.
- **Токен:** 32 случайных байта. В базе (`agent_sign_in_links`) только SHA-256; живёт 5 минут, работает один раз, привязан к подключению.
- **Лимиты:** 5 ссылок в час на подключение, 20 попыток за 10 минут с IP.
- **`/enter`:**
  - берёт токен из фрагмента и сразу убирает его из адресной строки. В запросах, журналах, Referer и аналитике токена нет;
  - `POST /api/auth/enter/preview` ничего не тратит: страница показывает, какая полка и от какого агента, и ждёт клика. Сканеры ссылок в почте и мессенджерах кнопок не нажимают;
  - если браузер уже вошёл в другую полку, страница показывает обе: «Остаться в «A»» или «Перейти в «B»». `POST /api/auth/enter` без `replace: true` отвечает 409 и сессию молча не заменяет;
  - после клика — сессия с `sessions.assurance='agent_link'` (слабая, 30 дней) и запись в журнале полки `auth.agent_link_used` с подключением, без токена;
  - после входа — плашка «Вы вошли по ссылке от агента <клиент>»;
  - устаревшая, использованная, чужая ссылка, выключенный переключатель или уже закреплённая полка дают один ответ: «Ссылка устарела — попросите агента новую».
- **Слабая сессия** смотрит полку и видит «Закрепить», но не может (`assertStrongSession`):
  - закреплять, объединять, привязывать и отвязывать способы входа;
  - подключать и отзывать агентов, выдавать токены, отвечать на согласие;
  - удалять аккаунт.
  Настоящий вход из неё открывает вашу полку и предлагает перенести работы (§ 8).

**Где об этом узнать:**
- `/signup`, экран после подключения, раздел «Агенты», плашка временной полки;
- `/connect`, `/llms.txt`, SKILL.md;
- описание `polka_context`: сразу после подключения агент один раз говорит «Если понадобится открыть полку в браузере — скажите мне «Открой мою Полку»».

**Отложено** (разбор docs/reviews/2026-09-24-auth, В7, В8, В11):
- ожидающие выборы хранятся в памяти процесса, а не в базе. Сессия цели при столкновении выдаётся до выбора;
- копирование объектов при слиянии идёт внутри транзакции с блокировками;
- на подтверждении отложенной привязки не показывается имя аккаунта поставщика.
