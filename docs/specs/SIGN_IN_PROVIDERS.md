# Вход через Яндекс ID, VK ID и SSO компании; ограничения входа по почте; заметки владельца

**Статус:** принято к реализации 24.09.2026.

**Зачем.**
- **Авторизация.** С 01.12.2023 владелец сайта — гражданин РФ обязан авторизовать пользователей из России одним из способов ч. 10 ст. 8 149-ФЗ: телефон, ЕСИА, ЕБС или информационная система российского владельца. С 07.07.2026 за нарушение штрафуют по ст. 13.55 КоАП. Вход по коду на иностранный почтовый ящик (Gmail) юридические СМИ приводят как нарушение.
- **Комментарии.** Тексты получателей, которые читают другие пользователи, по буквальному чтению ст. 10.1 делают Полку организатором распространения информации (ОРИ).

**Решения владельца:**
1. Добавить вход через Яндекс ID и VK ID. Новые регистрации по коду на почту — только на российских почтовых доменах. Существующие аккаунты продолжают входить.
2. На polochka.app заменить комментарии получателей заметками владельца.
3. Дать компаниям подключать единый вход, чтобы сразу получала доступ вся компания.

## 1. Внешние поставщики входа

### Общая схема

Полка — **клиент** OAuth 2.0 / OpenID Connect. С собственным OAuth-сервером Полки для агентов (`/oauth/*`, `oauth.ts`) эта часть не связана: у них разные таблицы, cookie и маршруты.

Поток — authorization code на сервере:
- `GET /api/auth/idp/:provider/start?next=/путь` — начало входа;
- `POST /api/auth/idp/:provider/link` — привязка к уже вошедшему аккаунту: нужна сессия и проверка Origin;
- Полка отвечает 303 на страницу авторизации поставщика;
- поставщик возвращает пользователя на `GET /api/auth/idp/:provider/callback`;
- Полка обменивает код на токен на сервере, читает профиль, выдаёт свою сессию (`polka_session`, как при входе по коду) и отвечает 303 на `next`.

**Защита:**
- **state** — 32 случайных байта. Сравнивается с тем, что лежит в cookie браузера, за постоянное время.
- **PKCE S256** — `code_verifier` из 32 случайных байт, всегда.
- **nonce** — для OIDC, проверяется в `id_token`. У Яндекс ID и VK ID `id_token` с nonce в веб-потоке нет, поэтому там защита — state и PKCE.
- **Состояние потока** хранится в cookie `polka_idp`, а не в базе:
  - шифрование AES-256-GCM, ключ выводится из `LINK_KEY` (HMAC с меткой назначения);
  - флаги HttpOnly, `SameSite=Lax` (иначе браузер не отдаст её на возврате с чужого сайта), `Path=/api/auth/idp`, 10 минут;
  - в cookie: поставщик, state, verifier, nonce, `next`, аккаунт для привязки и срок;
  - на возврате cookie стирается, повтор того же ответа отклоняется.
- **Строгий redirect URI** — `APP_ORIGIN + /api/auth/idp/<provider>/callback`. Он не собирается из запроса, у поставщика регистрируется точно такой же.
- **Где могут появиться секреты:**
  - токены поставщика и `client_secret` не попадают ни в URL, ни в журналы, ни в базу: access token живёт только в памяти запроса;
  - код авторизации приходит в query, так устроен OAuth. Он одноразовый, живёт минуты и без verifier бесполезен;
  - Полка отвечает 303, поэтому URL с кодом не остаётся в истории браузера. `Referrer-Policy: no-referrer` уже стоит на всех ответах.
- **Запросы к поставщику:**
  - только `https:` (`http:` допускается лишь для loopback в тестах);
  - таймаут 10 с, ответ не больше 256 КБ;
  - ошибки поставщика пользователю не пересказываются: только код причины на странице входа (`/signup?idp_error=…`).
- **Куда можно вернуться.** `next` проверяется так же, как `safeNext` в интерфейсе: только путь этой же установки.

### Яндекс ID

- Авторизация: `https://oauth.yandex.ru/authorize`. Параметры: `response_type=code`, `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method=S256`, `scope=login:email login:info`.
- Токен: `POST https://oauth.yandex.ru/token`. Параметры: `grant_type=authorization_code`, `code`, `code_verifier`, `client_id` и `client_secret` в Basic-заголовке.
- Профиль: `GET https://login.yandex.ru/info?format=json`, заголовок `Authorization: OAuth <token>`.
  - `id` — subject;
  - `default_email` — почта;
  - `real_name` или `display_name` — имя.
- Подтверждена ли почта, Яндекс явно не сообщает. Но адрес по умолчанию всегда подтверждён:
  - это собственный ящик Яндекса;
  - или ящик организации Яндекс 360 на домене, который организация подтвердила в DNS;
  - или адрес, с которым зарегистрировались «с любой почтой», — такой адрес подтверждают кодом.

  Поэтому по умолчанию `YANDEX_EMAIL_VERIFIED=true`. Оператор может выключить: тогда почта из Яндекса не связывает аккаунты и не даёт доступ по домену.
- Настройки: `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`. Без обеих вход выключен.

### VK ID

VK ID работает по OAuth 2.1 с обязательным PKCE. Актуальная документация VK ID (2026) указывает адреса на домене `id.vk.ru` (раньше — `id.vk.com`). Полка использует `id.vk.ru`; адреса можно переопределить для тестов.

- Авторизация: `https://id.vk.ru/authorize`. Параметры: `response_type=code`, `client_id`, `redirect_uri`, `state` (не короче 32 символов), `code_challenge`, `code_challenge_method=S256`, `scope=email`.
- Возврат: `code`, `state`, `device_id`.
- Токен: `POST https://id.vk.ru/oauth2/auth`, форма. Параметры: `grant_type=authorization_code`, `code`, `code_verifier`, `client_id`, `device_id`, `redirect_uri`, `state`. Ответ: `access_token`, `user_id`, `id_token` и др.
  - `client_secret` в потоке VK ID не передаётся: код защищён PKCE.
  - `state` в ответе должен совпасть с отправленным.
- Профиль: `POST https://id.vk.ru/oauth2/user_info`, форма `client_id`, `access_token`. Из `user` берутся `user_id` (subject), `email`, `first_name` и `last_name`.
- Признака подтверждения почты у VK ID нет (поле `verified` означает верифицированную страницу, а не почту). Поэтому по умолчанию `VK_EMAIL_VERIFIED=false`: почта из VK сохраняется в привязке, но не связывает аккаунты и не даёт доступ по домену. **Проверить** у VK, подтверждается ли почта аккаунта; если да — включить.
- Настройки: `VK_CLIENT_ID`. Вход выключен, пока он не задан.

### Свой OIDC (Keycloak, Avanpost, ADFS и др.) для своей установки

- **Настройки:**
  - `OIDC_DISCOVERY_URL` — адрес `…/.well-known/openid-configuration`;
  - `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`;
  - `OIDC_SCOPES` — по умолчанию `openid email profile`;
  - `OIDC_NAME` — подпись кнопки, по умолчанию «Единый вход компании».
- **Необязательно:**
  - `OIDC_ALLOWED_DOMAINS` — войти можно только с почтой этих доменов;
  - `OIDC_ORG_CLAIM` и `OIDC_ORG_VALUE` — вход только при `claim = value`. Если claim — массив (например, `groups`), значение должно в нём быть.
- **Discovery.** Документ читается при первом входе и кешируется на час. `issuer` в нём должен совпадать с префиксом адреса discovery.
- **Проверка `id_token`:**
  - подпись RS256, PS256 или ES256 по ключу из `jwks_uri` с тем же `kid`;
  - `iss`, `aud` (содержит `client_id`), `azp`, если `aud` несколько, `exp` и `iat` с допуском 2 минуты, `nonce`;
  - subject — `sub`, почта — `email`, подтверждена, только если `email_verified === true`.
- **Клиент:** confidential, `client_secret_basic`.

**Как компания подключает свой IdP.**
1. В IdP создать клиента OpenID Connect:
   - тип confidential, authorization code, PKCE S256;
   - redirect URI `https://<ваша Полка>/api/auth/idp/oidc/callback`;
   - scopes `openid email profile`;
   - в `id_token` передавать `email` и `email_verified`.
2. В `.env` установки задать `OIDC_*`, при желании — `OIDC_ORG_LIBRARY` (раздел 2).
3. Перезапустить. Кнопка с `OIDC_NAME` появится на странице входа.

### Яндекс 360 для бизнеса и VK WorkSpace

- **Яндекс 360 для бизнеса** в SSO — *поставщик услуг* (SAML 2.0): сотрудники входят в Яндекс 360 через IdP компании (Active Directory, Keycloak, Avanpost). Сторонним приложениям Яндекс 360 свой SAML или OIDC не отдаёт.

  Поэтому организация на Яндекс 360 входит в Полку **через Яндекс ID**:
  - аккаунт сотрудника — аккаунт организации с адресом `ivan@company.ru`;
  - если у компании настроен SSO в Яндекс 360, сотрудник по пути ещё раз проходит её IdP;
  - доступ всей компании даёт `ORG_DOMAINS=company.ru=…` (раздел 2).
- **VK WorkSpace / VK Teams.** Для входа в сторонние сервисы предусмотрен VK ID. Если у компании своя установка VK WorkSpace с OIDC-провайдером, её подключают как «свой OIDC». **Проверить** на конкретной установке.

### Аккаунты и привязки

Миграция `032_account_identities.sql` создаёт таблицу `account_identities`:
- `account_id` → accounts, `ON DELETE CASCADE`;
- `provider` (`yandex` | `vk` | `oidc`), `subject`;
- `email` — почта, которую поставщик сообщил при привязке, или NULL;
- `email_verified`;
- `created_at`, `last_used_at`;
- `UNIQUE(provider, subject)`.

Номер 031 занят параллельной веткой (`031_content_filter.sql`). Рецепты прав и проверки каталога принимают набор 1…32 с 031 или без него, так что ветки сливаются в любом порядке. После слияния обеих проверку можно сделать строгой.

**Что происходит при входе через поставщика:**
1. Привязка `(provider, subject)` уже есть → вход в её аккаунт, если он не заблокирован и не удаляется.
2. Идёт привязка из настроек (`link`) → привязка к вошедшему аккаунту. Если этот `subject` уже привязан к другой полке — отказ.
3. Поставщик **подтвердил** почту, и есть аккаунт с этой почтой → привязка к нему (так пользователь по коду на `ivan@yandex.ru` получает вход через Яндекс ID без второй полки).
4. Иначе — новый аккаунт:
   - `email` = подтверждённая почта, если она ни у кого не занята, иначе NULL;
   - `email_verified_at` ставится, только если почта подтверждена;
   - неподтверждённая почта аккаунту не присваивается;
   - действуют те же суточные лимиты новых полок (`EMAIL_SIGNUP_DAILY_LIMIT`, `EMAIL_SIGNUP_DAILY_PER_IP`);
   - в режиме `EMAIL_SIGNUP=invite` новая полка открывается только для приглашённой подтверждённой почты.

   Ограничение доменов (раздел 3) на поставщиков не действует: авторизацию проводит российская система.

**Отвязка.** «Способы входа» в настройках (`/settings/agents`): можно отвязать поставщика, если у аккаунта остаётся другой способ входа — почта или другая привязка.

**Удаление аккаунта.** Триггер миграции 032 удаляет привязки, как только у аккаунта появляется `deletion_requested_at`. Это происходит при подтверждении удаления, при восстановлении из копии (`register_restored_erasure`) и при окончательной очистке. Функцию `terminal_erase_account_metadata` 032 не переопределяет, поэтому с 031 и последующими миграциями не конфликтует.

## 2. Доступ компании

Настройки установки (оператора). Самостоятельная настройка домена администратором библиотеки отложена: без проверки владения доменом администратор чужой библиотеки мог бы собрать к себе сотрудников `sberbank.ru` и увидеть их почту.

- **`ORG_DOMAINS=company.ru=<uuid библиотеки>[:reader|curator], …`.**
  - Кто входит через поставщика с **подтверждённой** почтой этого домена (не поддоменов), становится участником библиотеки шаблонов с указанной ролью (по умолчанию reader).
  - Роль admin по домену не выдаётся.
  - Публичные почтовые домены (yandex.ru, mail.ru, gmail.com и т. п.) в `ORG_DOMAINS` запрещены: установка не запустится.
- **`OIDC_ORG_LIBRARY=<uuid>[:reader|curator]`.** Каждый, кто вошёл через «свой OIDC», становится участником этой библиотеки. IdP компании сам решает, кого пускать; дополнительно действуют `OIDC_ALLOWED_DOMAINS` и `OIDC_ORG_CLAIM`.

**Правила автоматического вступления:**
- Библиотека должна быть активной.
- Если участник уже есть или был исключён (строка membership существует в любом состоянии), ничего не меняется. Исключённого администратором домен обратно не добавит.
- Вступление пишется в журнал библиотеки (`template_library.domain_joined`) и в audit.
- Вход по коду на почту в библиотеку не добавляет. Сотрудник, который раньше входил по коду, добавится при первом входе через поставщика.

## 3. Вход по коду на почту

- **`EMAIL_SIGNUP_DOMAINS=any|ru-only|<список>`** — на каких доменах можно **открыть новую полку** по коду:
  - `any` — по умолчанию для своих установок, как раньше;
  - `ru-only` — по умолчанию в `deploy/hosted`. Встроенный список:
    - Яндекс: yandex.ru, ya.ru, yandex.com, yandex.by, yandex.kz, yandex.ua, narod.ru;
    - Mail.ru Group / VK: mail.ru, bk.ru, list.ru, inbox.ru, internet.ru, vk.com, vk.ru;
    - Рамблер: rambler.ru, ro.ru, lenta.ru, autorambler.ru, myrambler.ru, rambler.ua;
    - домен самой установки (хост `APP_ORIGIN`) и его родительский домен;
  - список — домены через запятую, `ru-only` можно указать элементом списка.
- **Существующие аккаунты** на любом домене по умолчанию входят по коду, как раньше: правовые пересказы спорят, распространяется ли требование на ранее зарегистрированных, а резкое отключение запирает людей.
  - **`EMAIL_LOGIN_DOMAINS=any|signup`.** `signup` отключает коды и для существующих аккаунтов вне разрешённых доменов. Перед этим попросите их привязать Яндекс ID или VK ID в «Способах входа».
- **Как выглядит отказ.**
  - Сервер отвечает на запрос кода одинаково, есть аккаунт или нет, и письмо на неразрешённый домен без аккаунта просто не уходит. Иначе по форме можно было бы узнать, у каких gmail-адресов есть полка.
  - Интерфейс знает список доменов из `/api/capabilities` (`emailSignupDomains`). При вводе адреса вне списка он заранее пишет: «Новые полки по почте открываются на адресах Яндекса, Mail.ru, Рамблера и VK. Если на этом адресе полки ещё нет, войдите через Яндекс ID или VK ID» и показывает эти кнопки.
- `EMAIL_SIGNUP=invite` и `EMAIL_SIGNUP_ALLOW` действуют как раньше. Адрес из `EMAIL_SIGNUP_ALLOW` открывает полку и вне списка доменов: это приглашение оператора.

## 4. Комментарии: `COMMENTS_MODE=on|owner-notes|off`

- **`on`** — по умолчанию для своих установок, как описано в [COMMENTS.md](COMMENTS.md).
- **`owner-notes`** — по умолчанию в `deploy/hosted`.
  - **Кто пишет.** Только владелец работы — на странице работы или по своей ссылке — и его агент: `polka_note`, `polka_comments`, `polka_resolve_comment`.
  - **Где живёт заметка.** Она привязана к ссылке, как ветка комментариев: получатели этой ссылки видят заметки только для чтения, без полей ввода.
  - **Реакции** выключены: не ставятся и не показываются.
  - **Писем** о заметках нет никому, кроме писем оператору о подозрительном тексте.
  - **Старые комментарии получателей и реакции** скрыты от всех, включая владельца и агентов, но не удалены. Если вернуть `on`, они снова видны.
  - **Запись получателя** (комментарий, ответ, реакция, удаление, «решено») отклоняется с 403: «На этой Полке получатели не оставляют комментарии. Напишите автору напрямую».
- **`off`** — обсуждений нет:
  - маршруты получателя отвечают 404;
  - оверлей во фрейм не добавляется;
  - владелец и агент получают пустой список с `mode: "off"`, запись отклоняется.

**Где видно режим:**
- `/api/capabilities` (`commentsMode`);
- ответы обсуждений (`mode`);
- `/llms.txt`, `SKILL.md`, описание MCP-инструментов и [connect-agents.md](../connect-agents.md).

**Интерфейс:**
- у получателя в `owner-notes` нет «Комментировать» и реакций на выделении, в ленте заголовок «Заметки автора»;
- у владельца — «Заметки».

Правовое основание — вариант «Г» из разбора рисков: заметки — контент владельца, а не обмен сообщениями между пользователями.

## 5. Интерфейс входа

- **Кнопки.** На `/signup` и на странице входа (`/?login=1`) кнопки «Войти с Яндекс ID», «Войти с VK ID» и, если настроен, «<OIDC_NAME>». Показываются, только если поставщик включён (`signInProviders` в `/api/capabilities`).
- **Текст кнопок** — официальный текст поставщиков: «Войти с …». Яндекс запрещает менять текст, цвет и иконку своей кнопки.
- **Цвета:**
  - Яндекс ID — чёрная кнопка с красным знаком «Я»;
  - VK ID — синяя `#0077FF` с белым знаком.
  - Иконки упрощённые, в SVG. Перед публикацией их стоит заменить официальными SVG из разделов «Оформление» у Яндекса и VK.
- **Возврат.** `next` передаётся поставщику через cookie потока и возвращается после входа. Поэтому подключение агента (`/oauth/consent?request=…`) продолжается после входа через поставщика так же, как после кода. Cookie запроса подключения (`/oauth`, Lax, 10 минут) переживает поход к поставщику.
- **Ошибки** показываются на `/signup` по коду `idp_error`:
  - `state` — запрос устарел или открыт в другом браузере;
  - `denied` — вы отменили вход;
  - `provider` — поставщик не ответил;
  - `blocked` — аккаунт заблокирован или удаляется;
  - `signup` — регистрация закрыта или по приглашению;
  - `domain` — почта не из разрешённого домена компании;
  - `linked` — этот аккаунт поставщика уже привязан к другой полке.

## 6. Персональные данные

В политику ([privacy.md](../legal/privacy.md)) добавляется новая строка:
- **Что хранится:** идентификатор пользователя у поставщика, почта и имя, которые он передал при входе.
- **Основание:** исполнение соглашения (п. 5 ч. 1 ст. 6 152-ФЗ) — вход в аккаунт.
- **Сколько хранится:** пока существует привязка или аккаунт.

Токены поставщика не сохраняются. Передача данных поставщику: Полка сообщает ему только, что пользователь входит в Полку (client_id и адрес возврата).

## 7. Проверки

- **Потоки с поддельными поставщиками** (локальный HTTP-сервер):
  - успешный вход и повторный вход;
  - несовпадение `state`;
  - отсутствующая или чужая cookie;
  - неверный `code_verifier` (поставщик отвечает ошибкой);
  - `nonce` и подпись `id_token` в OIDC;
  - неподтверждённая почта не связывает аккаунты;
  - подтверждённая почта связывает;
  - блокированный аккаунт;
  - привязка из настроек, повторная привязка к другой полке;
  - автоматическое вступление по домену с учётом исключённых.
- **Политика доменов:** новая полка вне списка не создаётся, существующая входит, `EMAIL_LOGIN_DOMAINS=signup`.
- **Режимы комментариев:** `on`, `owner-notes` (запись получателя, скрытие старых, реакции, письма, `polka_note`), `off`.
- **Миграция и права:** каталог, рецепты прав, привязки стираются при удалении аккаунта.
