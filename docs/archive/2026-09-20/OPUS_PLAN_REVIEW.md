## Основной вывод

Новый репозиторий, неизменяемые версии и отделение файловой выдачи от исполнения — хорошая основа. Ближайший выпуск перегружен: проверка сценария «принести результат агента и дать ссылку» сейчас ждёт полноценного рецепта-редактора, гостевых черновиков и части корпоративной логики.

**Рекомендуем уточнить первый срез до:** принести поддержанную работу → открыть → поделиться → обновить по той же ссылке → найти снова на полке. Затем отдельно проверять создание отчёта из примера, ручную правку, обсуждение и подключение агента. «Сохранить себе» у получателя остаётся гипотезой распространения, даже если не блокирует первый запуск.

Это рекомендация после обсуждения, **не новая конкурирующая очередь**. Действующие GOAL/REQUIREMENTS/DELIVERY_PLAN в этом проходе не переписаны. При следующем обновлении уточнить существующие P-задачи и условия выпуска; не заводить второй набор обязательных M/R-этапов. Сверка 195 строк PRD остаётся справочной базой, а не 195 активными задачами первого выпуска.

## Что предлагаем изменить

«Согласовано» ниже означает согласие Codex и Opus в обсуждении, не отдельное утверждение владельца и не выполненную реализацию.

| Предложение | Зачем | Где уточнить |
|---|---|---|
| Отделить первый допущенный сценарий A от редактора B | Получить настоящий пользовательский сигнал до разработки большого редактора и guest claim | GOAL, DELIVERY_PLAN M1/M2, P09, LAUNCH |
| Обычная ссылка ведёт на явно выбранную автором опубликованную версию; есть отдельная pinned-ссылка | Исправление опечатки не требует рассылать новый адрес; обычный save не меняет внешний результат молча | F07, J06, P07, ARCHITECTURE §4 |
| «Обновить по ссылке» переключает указатель после проверок; открытая сессия остаётся на одной revision | HTML, CSS и изображения не смешиваются между версиями; официальные releases неизменяемы | P07/P08, Revision/ShareLink/Grant |
| Личный tenant и default workspace; папки сначала организуют работы без собственных ACL | Сохранить корпоративное владение и будущую структуру, отложив сложное наследование прав | P02/P03/P06/P10, F02/F03/F06 |

| Добавить «Вставить HTML» как кандидат входа рядом с файлом и ZIP | Для части пользователей копирование кода может быть проще скачивания; это гипотеза для проверки | INTERFACES, J01, P05 |
| Сначала внешний агент → MCP → приватная работа/предложение и ссылка владельцу | Не ждать pairing/runner/lease и встроенного чата, чтобы агент мог сохранить результат | P20 перед сложными частями P13 |
| Для произвольного HTML сначала честная замена версии; прямую правку проверять по типу исходника | Изменение DOM, построенного React/JS, не доказывает сохранение изменения в коде | F09, P09, INTERFACES |

Основа, которую упрощение не отменяет: серверное «только владелец / явно разрешённый доступ», изоляция tenants, owning tenant отдельно от `createdBy`, проверка точных итоговых байтов, неизменяемые revisions, идемпотентность, квоты, audit и восстановление. Публичный share остаётся человеческим действием. Внешний агент может вернуть owner-only адрес candidate без создания публичного grant.

Внутренняя установка раннего среза не называется корпоративно готовой: SSO, классификация, наследование прав, required approvals и операторская приёмка должны появиться до соответствующих обещаний.

## Где Opus уточнил первый отзыв

В первом раунде были слишком сильные утверждения. После возражений Codex Opus признал:

- Worker обложек уже описан. Не хватает конкретной маршрутизации HTML-пакета: относительные пути, origin, grants/cookies, localStorage, отзыв и репутационные границы домена.
- Networkless runtime не обязательно ломает библиотеки: прежний исполнитель запускал React/Chart.js с заранее собранными зависимостями. Доля таких входов в реальном спросе неизвестна; стоимость и качество потока кадров требуют измерения.
- CSP и отдельный домен не доказывают отсутствие исходящей сети. В прежнем тесте Lanka STUN проходил при заблокированных parent/cookies/fetch/Worker. Это не доказательство захвата origin приложения и не полный security-аудит.
- Одних корпоративных полей недостаточно: минимальные права реально проверяются. Один default workspace без UI не требует сложного онбординга.
- Проверка checksum не заменяет валидацию типа, путей и целостности пакета на exact final bytes после копирования из staging.

Таким образом, первый отзыв не следует применять буквально без второго раунда.

## Открытый вопрос: приватный HTML и сеть

**Позиция Opus:** личный приватный HTML можно показывать в браузере, изолировав от учётных данных приложения и других работ, но честно не обещая no-egress. Строгий режим — по корпоративной политике. Опасение Opus: если публичный просмотр окажется удобнее приватного, пользователь начнёт публиковать работу ради лучшего отображения.

**Позиция Codex:** «приватно» определяет аудиторию и само по себе не доказывает запрет сети. Но простая пометка не заменяет защиту: запросы могут раскрыть не только IP, но и содержание, доступное исполняемому коду. Нельзя автоматически принять browser execution для закрытых данных или назвать CSP строгой изоляцией. Также нельзя заставлять публиковать материал, чтобы он нормально открылся.

**Практический результат:** не объявлять победителя архитектурно заранее. Измерить нативный браузерный профиль и строгий runtime на одном корпусе; сравнить совместимость, качество, доступность, задержку, стоимость и две разные границы: доступ к данным приложения/чужим работам и отсутствие исходящей сети. Если строгий профиль не проходит по качеству/стоимости, явно ограничить поддержанный формат либо отдельно выбрать и точно описать модель личного сервиса. Ослабление обещания для приватных данных не считается согласованным этим обсуждением.

## Три проверки до большого редактора

1. **Просмотр настоящих артефактов.** Собрать разрешённый корпус HTML/ZIP от реальных агентов с разными зависимостями. Проверить браузерный и строгий профили на телефоне/компьютере: фактические взаимодействия, relative paths, fonts/images/charts, доступность, стоимость. Заранее зафиксировать порог совместимости и лимиты. Не прошёл профиль — сузить форматы, не выдавать снимок за прототип.
2. **Одна ссылка и две версии.** Автор сохраняет исправление, внешний результат не меняется. Затем явно обновляет ссылку; новый получатель видит новую версию, текущая сессия не смешивает ресурсы. Проверить revoke/TTL, private metadata, обложку в мессенджере и доступность в целевых сетях.
3. **Сохранение внешним агентом.** После стабилизации file/revision API проверить один настоящий MCP-клиент: контекст папки/recipe, запись candidate, повтор, приватная ссылка владельцу. Публичный доступ не создаётся агентом; запуск из чата Полки не является предпосылкой этого опыта.

Ни одна из этих проверок в рамках обсуждения не выполнялась. Это ближайшие основания для принятия реализации.
